## 확인하려던 것

같은 재고를 200개 요청이 동시에 차감할 때, **동시성 제어 9가지가 각각 정합성을 지키는지와 얼마나 느려지는지.**

## 실험 설계

- Testcontainers MySQL 8.0.36 (Redis 케이스는 Redis 7.2.5 추가)
- 쿠폰 재고 **200개**, 기본 요청 **200개**
- 성공/실패를 반환하는 케이스(원자적 UPDATE·Redis Lua)는 **250 요청**으로 초과분까지 확인
- `ExecutorService` + `CountDownLatch`로 출발선을 맞춰 동시 요청 재현
- 측정: 테스트 콘솔 `ms`

## 결과

| 방식 | 실행 시간 | 배수 |
|---|---|---|
| Redis Lua 원자 차감 | **41.1ms** | 0.25× |
| 락 없음 (정합성 깨짐) | 163.2ms | 1× |
| 원자적 UPDATE | **369.1ms** | 2.3× |
| 비관적 락 (`FOR UPDATE`) | 429.2ms | 2.6× |
| synchronized | 933.3ms | 5.7× |
| 네임드 락 (`GET_LOCK`) | 1101.3ms | 6.7× |
| Redis 분산락 (`SET NX`) | 1312.5ms | 8.0× |
| Redisson (`RLock`) | 1312.5ms | 8.0× |
| **낙관적 락 (재시도)** | **3156.1ms** | **19.3×** |

🟢 "락 없음" 163ms는 **비교 기준이지 선택지가 아니다.** 두 요청이 같은 `quantity = 200`을 읽고 각각 199를 써서 최종 재고가 198이 아니라 199가 된다 → [[Lost Update]]

## 해석

🟡 **경합이 심할수록 낙관적 락이 최악이다.** 200개 요청이 한 로우를 다투면 충돌 → 재시도가 반복되며 19배까지 벌어진다. [[낙관적 락]]은 "충돌이 드물 때"라는 전제가 붙는 이유가 이 숫자다.

🟢 **Redis Lua가 락 방식보다 30배 빠른 건 락을 안 쓰기 때문이다.** 차감 자체가 원자적이라 상호배제가 필요 없다. 같은 이유로 [[원자적 UPDATE로 푸는 동시성]]도 락 방식들보다 빠르다(369ms vs 429~1312ms).

🟢 **분산락은 왕복 비용을 낸다.** [[Redis 분산락]]과 Redisson이 나란히 1312ms인 건 둘 다 네트워크 왕복 + 락 획득/해제가 요청마다 붙기 때문이다. 단일 프로세스면 `synchronized`(933ms)가 더 싸다.

💬 순서를 정리하면 **원자적 연산 > DB 락 > 분산락 > 낙관적 락(경합 시)**. "분산락부터 꺼내는" 습관이 왜 비싼지 여기서 보인다.

## 한계

🔴 **단일 실행의 예시 출력이지 벤치마크가 아니다.** 반복 측정·워밍업·분산이 없어 절대값으로 읽으면 안 된다. JIT 워밍업 전 구간이 섞여 있을 가능성도 그대로 남아 있다.

🔴 **경합 조건이 극단적이다.** 200 요청이 **한 로우**를 다투는 최악의 시나리오다. 실무의 일반적인 부하에서는 낙관적 락이 이렇게까지 지지 않는다. 이 표는 "경합이 심할 때의 순위"로만 읽는다.

🔴 로컬 Testcontainers라 네트워크 지연이 실제 인프라와 다르다. Redis 왕복 비용이 실제보다 **작게** 나왔을 가능성이 높다.

🔴 정합성 측면은 "지켰다/깨졌다" 이분법으로만 확인했고, 처리량(TPS)이나 p95 같은 분포는 재지 않았다.
