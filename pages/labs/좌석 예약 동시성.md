## 확인하려던 것

확정 쓰기가 **한꺼번에 RDB로 몰릴 때** 무엇이 병목이 되는가. 그리고 Redis로 선점하고 Kafka로 버퍼링하면 그 병목이 어디로 옮겨 가는가.

## 실험 설계

케이스 4가 이 모듈의 본체다. 🟢 **느린 DB를 결정적으로 흉내 냈다.**

```java
registry.add("spring.datasource.hikari.maximum-pool-size", () -> 2);
registry.add("spring.datasource.hikari.connection-timeout", () -> 250);
registry.add("seat.db.write-delay-millis", () -> 20);
```

사용자마다 **다른 좌석 100개**를 한꺼번에 요청한다.

> 🔴 원저자 주: *완전한 재현(RDB CPU 폭주 → 실제 장애)은 nGrinder·AWS 같은 실부하 환경이 필요하다. 이 테스트는 그 **구조적 인과**를 단위 테스트에서 결정적으로 재현한다.*

## 결과

```text
직접 쓰기  - 요청 반환까지 298ms, 성공 12건, 실패(타임아웃 등) 88건
Kafka 경유 - 요청 반환까지  21ms, 실패 0건 / DB 전부 확정까지 3780ms
```

| | 직접 쓰기 | Kafka 경유 |
|---|---|---|
| 요청 반환 | 298ms | **21ms** (14배 빠름) |
| 실패 | **88건** | **0건** |
| 최종 확정 | 12건 | **100건** (3780ms 소요) |

🟢 **직접 쓰기** — 요청 스레드가 느린 DB에 묶인다 → 작은 커넥션 풀(2) 고갈 → `connection-timeout`(250ms) 초과 요청이 실패. **요청 반환 시간이 DB 속도에 묶인다.**

🟢 **Kafka 경유** — 요청 경로는 Redis 선점 + publish만 하고 즉시 반환. 몰린 쓰기는 토픽이 받아 두고 Consumer가 **DB 속도에 맞춰 천천히 소진**한다.

## 해석

🟡 **Kafka가 쓰기를 빠르게 만든 게 아니다.** DB 확정은 여전히 3780ms 걸린다. 바뀐 것은 **누가 기다리느냐**다 — 사용자 요청 스레드가 아니라 Consumer가 기다린다.

🟡 그래서 이건 **처리량 개선이 아니라 백프레셔 흡수**다. 버스트를 토픽이 받아 두고 평탄화한다. 🔴 지속적으로 유입이 처리량을 넘으면 토픽이 계속 밀리고 컨슈머 랙만 커진다 — **버스트에는 듣지만 과부하에는 안 듣는다.**

🟢 비동기의 대가도 그대로 나온다 — 요청은 21ms에 성공을 받지만 **그 시점에 DB에는 아직 없다.** [[최종적 일관성]]이고, 사용자에게 무엇을 보여줄지가 설계 사항이 된다.

🟢 **실패 처리**: Consumer의 DB 확정이 실패하면 `FailedEvent`로 기록해 유실만 막는다. 🔴 원저자가 *"재처리 배치는 아직 없음(향후 구현 예정안)"*이라고 명시했다 — [[실패 사실의 기록]]의 절반만 구현된 상태다.

## 한계

🔴 **실부하가 아니다.** 커넥션 풀 2, 지연 20ms로 흉내 낸 "느린 DB"다. 원저자가 스스로 밝혔듯 구조적 인과의 재현이지 성능 수치가 아니다.

🔴 **재처리 배치가 없다.** `FailedEvent`는 쌓이기만 하고 아무도 소진하지 않는다. 유실은 막았지만 복구는 미구현이다.

🔴 **Kafka 자체의 실패를 다루지 않았다.** 브로커 장애, publish 실패, 컨슈머 리밸런싱 중 중복 처리는 범위 밖이다.

🔴 **Redis 선점(`SADD`)과 DB 확정 사이의 불일치**를 다루지 않았다. 선점은 됐는데 확정이 영영 실패하면 그 좌석은 매달린다 — [[TCC]]의 "매달림"과 같은 구조.

🔴 수치는 예시 출력이고 환경에 따라 달라진다.
