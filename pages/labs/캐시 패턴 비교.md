## 확인하려던 것

읽기 miss를 **누가 처리하느냐**, 쓰기를 캐시에 **언제 반영하느냐**로 패턴이 갈릴 때 각각 무엇이 관찰되는지. 그리고 캐시가 무너지는 **네 가지 실패 모드**를 재현할 수 있는지.

## 실험 설계

- Java 21, **외부 Redis 없이** `InMemoryCache` + `InMemoryProductStore`
- 대상 데이터: `Product`
- 관찰값: **캐시 hit/miss 횟수 · 저장소 read/write 횟수 · Write Behind pending write 개수 · 동시 miss 시 저장소 load 횟수 · TTL 만료 시점의 active key 개수**

> 🔴 순수 인메모리라 **네트워크·직렬화 비용이 전혀 없다.** 이 실험이 재는 것은 시간이 아니라 **호출 횟수와 상태**다.

## 결과

### 읽기 miss를 누가 처리하나

| 패턴 | miss 처리 주체 | 흐름 |
|---|---|---|
| Cache Aside | **서비스 코드** | `cache.get` → miss → `store.findById` → `cache.put` |
| Read Through | **캐시 접근 계층** | `cache.get` → miss → loader 호출 → `cache.put` |

🟡 핵심 차이는 **누가 저장소를 호출하느냐** 하나다. Read Through에서 서비스는 캐시 계층만 부르고, 저장소 존재를 모른다.

> 🔴 이 예제의 `ReadThroughCache`는 서비스 **바깥의 캐시 접근 계층**이다. **외부 Redis 자체가 DB loader를 아는 구조가 아니다.** 실무에서는 Caffeine/Ehcache 같은 loading cache, 또는 Redis 앞에 둔 앱 공통 래퍼로 나타난다.

### 쓰기를 언제 반영하나

| 패턴 | 쓰기 흐름 | 쓰기 직후 캐시 | 저장소 반영 |
|---|---|---|---|
| Write Through | `store.save` → `cache.put` | **최신 값 있음** | 요청 안에서 즉시 |
| Write Around | `store.save` → `cache.evict` | **해당 key 없음** | 요청 안에서 즉시 |
| Write Behind | `cache.put` → pending 추가 → `flush` | 최신 값 있음 | **나중에** |

🟢 `WriteBehindProductService`의 관찰 포인트가 이 패턴의 정체를 그대로 보여준다 — **쓰기 직후 저장소는 이전 값, 캐시는 최신 값.**

### 네 가지 실패 모드

| 문제 | 언제 터지나 | 예제 방어 |
|---|---|---|
| Race Condition | 읽기와 쓰기가 교차해 **오래된 값이 뒤늦게** 캐시에 들어갈 때 | `VersionedCache` |
| Cache Stampede | 인기 키가 **동시에 miss/만료**될 때 | `SingleFlightCache`, `RefreshAheadCache` |
| Cache Penetration | **존재하지 않는 키**가 반복 조회될 때 | `NegativeCachingCache`, `BloomFilter` |
| Cache Avalanche | 많은 키가 **같은 시각에 만료**될 때 | `ExpiringCache` + TTL jitter |

🟢 `StaleCachePutRaceTest`가 Race Condition을 재현한다 — 읽기 A가 miss 확인 후 v1을 조회하는 사이 쓰기 B가 v2 저장 + evict를 끝내고, **A가 뒤늦게 v1을 put**한다. 최종적으로 캐시 v1 / 저장소 v2. `VersionedCache`는 더 낮은 버전의 put을 거부하고 `rejectedPuts()`로 횟수를 노출한다.

## 해석

🟡 **패턴 이름이 다섯 개지만 축은 둘뿐이다** — "읽기 miss를 누가 처리하나"와 "쓰기를 캐시에 어떻게 반영하나". 그래서 실무에서는 항상 **조합**으로 쓴다.

| 상황 | 조합 |
|---|---|
| 일반적인 조회 캐시 | **Cache Aside + Write Around** |
| 캐시 로딩 로직 공통화 | Read Through + Write Around |
| 쓰기 직후 바로 읽는 요청이 많음 | + Write Through |
| 쓰기는 많고 조회는 적음 | + Write Around |
| 쓰기 처리량이 매우 중요 | + Write Behind **+ 영속 큐** |

🟢 **`CacheAsideProductService`와 `WriteAroundProductService`는 코드가 거의 같다.** 이름이 다른 이유는 관찰 대상이 달라서다 — 앞은 *읽기 miss를 누가 처리하는지*, 뒤는 *쓰기 때 캐시를 채우는지*. 💬 패턴 이름을 코드 모양으로 외우면 이 지점에서 헷갈린다.

## 한계

🔴 **시간을 재지 않았다.** 관찰값이 전부 횟수·개수다. "어느 패턴이 빠른가"는 이 실험으로 답할 수 없다.

🔴 **인메모리라 실제 캐시의 비용이 빠져 있다.** 네트워크 왕복, 직렬화/역직렬화, Redis 단일 스레드 경합이 전부 없다. → [[Spring Cache Redis]]가 그 층을 본다.

🔴 **단일 프로세스다.** 여러 인스턴스가 같은 캐시를 볼 때 생기는 문제(로컬 캐시 불일치, 분산 락 필요성)는 재현되지 않는다.

🔴 Write Behind의 **유실**은 재현하지 않았다. pending write 개수만 관찰하고, 플러시 전에 프로세스가 죽는 시나리오는 없다.
