## 확인하려던 것

**쪼개기 전에는 무엇이 공짜였는가.** 좌석·지갑·예약을 하나의 로컬 트랜잭션으로 처리하는 기준선을 세워, 이후 [[분산 트랜잭션 기준선 - MSA]]에서 무엇이 사라지는지 대조할 수 있게 만든다.

## 실험 설계

- MySQL 하나. 좌석(`WorkshopSeat`)·지갑(`Wallet`)·예약(`Reservation`)이 같은 DB
- **예약 생성과 실행을 나눈다** — 생성은 `CREATED`로 커밋, 실행은 별도 트랜잭션
- 실행 시 예약 row를 `SELECT FOR UPDATE`로 잡는다

🟢 생성/실행을 나눈 게 설계의 핵심이다. 생성 시점에 `reservationId`가 발급되므로 **실행을 몇 번 다시 시도해도 같은 요청**임을 알 수 있다 — [[멱등성]]의 "고유 식별자 부여" 단계가 API 구조로 들어가 있다.

## 결과

### 실패하면 실행 트랜잭션만 롤백된다

```
BEGIN
  Reservation 1 SELECT FOR UPDATE
  좌석 예약 → reservedCount 증가
  wallet.debit(60,000, ledgerKey = reservation:1:debit)
    → NotEnoughCreditException
ROLLBACK
```

| 대상 | 상태 |
|---|---|
| `Reservation` | **`CREATED` 유지** (삭제되지 않음) |
| 좌석 | 원상 복구 |
| 지갑·원장 | 변경 없음 |

🟢 **예약이 남는 게 의도된 설계다.** 잔액 충전이나 장애 해소 후 **같은 `reservationId`로 다시 실행**할 수 있다. 실패가 곧 요청의 소멸이 아니다.

### 재실행은 `SELECT FOR UPDATE`가 직렬화한다

같은 예약을 동시에 두 번 실행해도 [[비관적 락]]이 줄을 세운다. 앞 트랜잭션이 커밋한 뒤 뒤 트랜잭션이 상태를 다시 읽으므로, 이미 확정된 예약은 그 사실을 보고 빠진다.

## 해석

🟡 **`@Transactional` 한 줄이 이 모든 걸 대신하고 있다.** 세 도메인이 같은 커넥션을 쓰는 덕에 원자성이 공짜로 얻어진다 — 이 사실이 [[분산 트랜잭션이 필요한 순간]]의 출발점이다.

🟡 **이 기준선에서 이미 두 가지를 직접 만들었다는 게 중요하다** — 고유 식별자(`reservationId`)와 직렬화(`FOR UPDATE`). 🔴 **트랜잭션이 대신해 주는 건 원자성뿐이고, 중복 실행 방지는 모놀리식에서도 공짜가 아니다.**

## 한계

🔴 **단일 DB라 이 실험 자체에는 분산 요소가 없다.** 대조군으로서만 값을 한다.

🔴 성능을 재지 않았다. 이후 MSA·2PC·TCC와 비교할 시간 기준선이 없다는 뜻이다.

🔴 `FOR UPDATE`가 만드는 락 대기 시간이나 데드락은 관찰하지 않았다.
