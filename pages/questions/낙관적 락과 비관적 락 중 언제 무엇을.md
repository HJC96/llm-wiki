## Q

낙관적 락과 비관적 락 중 언제 무엇을 쓰나요?

## A (30초)

**충돌 빈도로 가릅니다.** 충돌이 드물면 낙관적 락으로 저장 시점에만 버전을 비교하고, 상시 경합하는 데이터면 비관적 락으로 줄을 세우는 게 쌉니다. 낙관적 락은 아무것도 잠그지 않는 대신 실패했을 때 재시도든 거절이든 처리를 애플리케이션이 정해야 하고, 비관적 락은 잠그는 대신 락을 쥔 시간이 곧 다른 요청의 대기 시간이 됩니다.

직접 재보니 200 요청이 한 로우를 다투는 상황에서 낙관적 락이 **3156ms**, 비관적 락이 **429ms**로 7배 차이가 났습니다. "충돌이 드물 때만"이라는 전제가 빈말이 아니었습니다.

## A (3분)

**기준은 두 축입니다 — 충돌 확률과, 실패했을 때 잃는 작업량.**

충돌 확률이 낮으면 낙관적 락이 유리합니다. 매번 락을 잡는 비용을 안 내고, 평소엔 여러 사용자가 자유롭게 작업하다 저장 시점에만 버전을 비교하면 되니까요. 반대로 인기 상품 재고나 선착순 쿠폰처럼 **항상** 경합하는 데이터는 낙관적 락이 재시도만 반복하며 스레드와 커넥션을 태웁니다. 이때는 줄 세우는 쪽이 싸고, 실제로 [[선착순 쿠폰 발급 동시성]] 실험에서 7배 차이로 나타났습니다.

**두 번째 축이 면접에서 덜 나오는데 실무에선 더 중요합니다.** 낙관적 락은 충돌을 **작업이 끝난 뒤에** 알려 줍니다. 30분 편집한 사용자가 저장 버튼을 눌렀을 때 409를 받으면 그 30분을 통째로 잃습니다. Fowler가 이걸 두고 그런 일이 잦으면 시스템이 곧 인기를 잃는다고 표현했는데, 편집 시간이 긴 화면이라면 충돌 확률이 낮더라도 비관적 방식을 검토할 이유가 됩니다.

**층위를 구분하는 것도 중요합니다.** "락"이라는 한 단어가 서로 다른 셋을 가리킵니다.

| | 잠그는 것 | 수명 |
|---|---|---|
| [[비관적 락]] (`FOR UPDATE`) | DB 로우 | 트랜잭션 |
| [[네임드 락]] (`GET_LOCK`) | 문자열 이름 | 세션 |
| [[Redis 분산락]] | Redis 키 | TTL |
| [[낙관적 락]] (`@Version`) | **아무것도 안 잠금** | — |

그리고 조회와 저장이 **다른 요청**이면 트랜잭션 종속 락은 애초에 쓸 수 없습니다. 그 구간을 지키려면 버전 값을 클라이언트가 들고 다니는 [[Optimistic Offline Lock]]이나 락 레코드를 남기는 [[Pessimistic Offline Lock]]처럼 트랜잭션 경계를 넘어서는 수단이 필요합니다.

**셋 다 아닌 경우도 있습니다.** 읽은 값이 계산에 필요 없다면 `UPDATE ... SET qty = qty - 1 WHERE qty > 0` 한 방으로 틈 자체를 없애는 게 가장 쌉니다 → [[원자적 UPDATE로 푸는 동시성]] (369ms로 셋 중 가장 빨랐습니다).

## 꼬리질문

- **"낙관적 락 재시도는 어디에 두나요?"** → 트랜잭션 **밖**입니다. `ObjectOptimisticLockingFailureException`은 flush/commit 시점에 터지므로 같은 트랜잭션 안에서 잡아 봐야 이미 되돌릴 수 없습니다. Facade가 트랜잭션을 닫고 새로 여는 경계를 만듭니다 → [[낙관적 락]]
- **"재시도 횟수는 왜 제한하나요?"** → 무제한이면 경합이 심한 키에서 스레드가 재시도만 반복하며 커넥션을 붙들어 서비스 전체를 끌어내립니다.
- **"비관적 락의 위험은?"** → 데드락(접근 순서 고정으로 처방)과 갭 락. MySQL InnoDB는 REPEATABLE READ에서 인덱스 범위에 갭 락을 함께 겁니다.
- **"조회와 저장이 다른 요청이면요?"** → [[JPA @Version과 Optimistic Offline Lock의 차이]]
- **"락을 걸었는데 인스턴스가 여러 대면요?"** → DB 락은 여전히 유효하지만 애플리케이션 락은 [[Redis 분산락]]으로 올라가야 합니다.
