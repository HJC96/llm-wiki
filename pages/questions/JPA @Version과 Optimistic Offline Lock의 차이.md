## Q

"버전 컬럼 비교했다면 그거 그냥 낙관적 락 아닌가요?"

> 실무에서 편집 충돌 제어를 설명하면 거의 확실히 따라오는 질문. 알고리즘이 같아 보이기 때문이다.

## A (30초)

**알고리즘은 같고 정합성을 보장하는 단위가 다릅니다.** JPA의 낙관적 락은 하나의 시스템 트랜잭션 안에서 갱신 충돌을 감지합니다. 제 경우는 조회와 저장이 **별도 요청**이라, 조회 트랜잭션에서 발급한 버전을 클라이언트가 편집하는 내내 들고 있다가 저장 시점에 되돌려주는 구조로 확장했습니다. 지키는 단위가 DB 트랜잭션이 아니라 **업무 트랜잭션 전체**라는 점이 차이고, Fowler가 Optimistic Offline Lock이라고 부르는 게 정확히 이 형태입니다.

## A (3분)

**충돌 창의 길이가 다릅니다.**

`@Version`만 붙인 경우, 엔티티를 읽고 flush할 때까지가 충돌 창입니다. 한 트랜잭션 안이니 길어야 수 밀리초죠. 그런데 화면 편집은 조회 요청과 저장 요청 사이에 **사람의 시간**이 낍니다. 응답이 나가는 순간 트랜잭션도 영속성 컨텍스트도 사라지므로, 그 구간은 `@Version`이 보호하지 못합니다.

**그래서 버전을 트랜잭션 밖으로 내보냅니다.** 조회 응답에 버전을 실어 주고, 저장 요청이 그 버전을 다시 가져오게 합니다. 트랜잭션이 못 넘는 경계를 값이 대신 넘는 셈입니다. HTTP 의미론으로는 `ETag` / `If-Match`가 정확히 이 역할입니다. 서버는 `UPDATE ... WHERE id = ? AND version = ?`의 affected rows가 0이면 충돌로 판정하고 **409 Conflict**로 응답합니다.

**검증과 갱신만 한 트랜잭션 안에 있으면 됩니다.** 조회까지 묶을 필요가 없다는 게 이 패턴이 성립하는 이유입니다. 원문 표현으로는 *"So long as the validation and the updates occur within a single system transaction the business transaction will display consistency."*

**락 단위를 어디로 잡을지가 실제 설계 판단입니다.** 화면이 탭으로 나뉘고 탭마다 독립 저장이 필요하다면, 애그리거트 루트에 버전 하나만 두는 순간 탭 A의 저장이 전체 버전을 올려 버려 탭 B를 편집하던 사람이 **자기가 만지지도 않은 변경으로** 튕깁니다. 그래서 충돌 감지 범위를 탭 단위로 좁혔습니다. PoEAA에서 연관 객체를 한 락으로 묶는 걸 Coarse-Grained Lock이라고 부르는데, 그 반대 방향으로 간 선택입니다.

**대가도 같이 말해야 설득력이 있습니다.** 🔴 충돌이 작업 끝에서만 드러나므로 편집이 길면 실패 비용이 큽니다. 그래서 409를 띄울 때 사용자의 입력을 날리지 않고 보존한 채 최신 데이터와 비교할 수 있게 하는 게 보완책이고, 편집 시간이 더 길어지면 [[Pessimistic Offline Lock]] 쪽으로 판단이 뒤집힐 수 있습니다.

## 꼬리질문

- **"왜 비관적 락이 아니었나요?"** → 편집 시작부터 자원을 점유하면 사용자가 화면을 열어 둔 시간만큼 다른 사람이 차단됩니다. 게다가 `FOR UPDATE`는 트랜잭션이 끝나면 풀리므로 요청이 나뉜 구조에서는 애초에 그 구간을 덮지 못합니다 → [[네임드 락]]
- **"네임드 락은 왜 안 썼나요?"** → 세션 종속이라 구간을 덮을 수는 있지만, 화면을 여는 시점부터 저장까지 커넥션과 락을 붙잡습니다. 요구사항이 "편집은 자유롭게, 저장 시점에 선착순"이었으므로 점유가 아니라 검증으로 푸는 게 맞았습니다.
- **"동시 저장을 테스트로 어떻게 재현했나요?"** → 두 갈래입니다. 같은 버전을 들고 순차 호출하면 결정적으로 재현되고(논리적 동시), DB 레벨 보장까지 증명하려면 `CountDownLatch`로 출발선을 맞춰 N개를 동시에 던지고 **성공 1 / 충돌 N-1**을 단언합니다. 누가 이기는지는 비결정적이어도 몇 개가 이기는지는 결정적이라 CI에서 흔들리지 않습니다.
- **"그 테스트에서 걸리기 쉬운 건?"** → 테스트 메서드에 `@Transactional`을 붙이면 커밋이 안 돼 다른 스레드가 데이터를 못 봅니다. 각 스레드가 자기 트랜잭션을 갖도록 서비스 레이어를 통해 호출해야 하고, 커넥션 풀이 스레드 수보다 작으면 풀 고갈로 테스트가 멈춥니다.
- **"보상 트랜잭션으로 풀 수도 있지 않나요?"** → 생성한 뒤 되돌리는 방식이라 사용자에게는 문서가 생겼다 사라지는 경험이 됩니다. 아예 막는 쪽이 깔끔하고, 되돌릴 대상이 없으므로 [[Saga 패턴]]이라고 부를 수도 없습니다.
