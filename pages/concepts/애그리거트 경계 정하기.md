## 한 줄 정의

> 🟡 **함께 저장되고 함께 지켜져야 하는 것들을 한 덩어리로 묶고, 바깥은 오직 루트를 통해서만 그 안을 만지게 하는 것.** 애그리거트는 일관성의 단위이자 **접근 통제의 단위**다.

## 왜 필요한가

경계를 정하지 않으면 두 가지가 무너진다. ① 내부 엔티티를 아무 데서나 만들고 바꿔서 불변식을 어디서 지키는지 알 수 없게 된다. ② 리포지토리가 엔티티 수만큼 늘어나고, 어느 것을 먼저 저장해야 하는지가 호출자의 책임이 된다.

> 🟡 애그리거트는 **애플리케이션(헥사곤)의 단위**이기도 하다. 애그리거트마다 별도 패키지를 두고, 그 내부 기능에는 Provided Interface를 타고만 접근하게 하면 [[헥사고날 아키텍처]]와 자연스럽게 맞물린다.

## 어떻게 동작하는가

### 무엇을 같은 패키지에 둘 것인가

```
domain/
 ├ member/       Member, MemberDetail, MemberRegisterRequest, MemberStatus,
 │               PasswordEncoder, Profile, EmailDuplicatedException
 └ shared/       Email
application/
 └ member/       포트 + 구현
```

> 💬 **`Email`은 왜 shared이고 `EmailDuplicatedException`은 왜 member인가?** `Email`은 다른 애그리거트에서도 값 객체로 쓰일 가능성이 크다. 반면 "이메일이 중복되면 안 된다"는 규칙은 **이메일이 회원에서 식별자로 쓰이기 때문에** 생긴 것이라 member 도메인의 로직이다. 나중에 여러 도메인에서 쓰이면 그때 분리한다.

### 루트가 내부 엔티티의 모든 책임을 진다

> 🟡 외부는 `MemberDetail`을 직접 만들거나 조작하지 않는다. **항상 루트를 통한다.** 설계 가이드를 지키자는 약속만으로는 실수하므로 **언어 차원에서 막는다** — 내부 엔티티의 생성·변경 메서드를 `package-private`으로 둔다. 같은 패키지인 `Member`에서는 여전히 쓸 수 있다.

```java
// MemberDetail — package-private 정적 팩토리
static MemberDetail create() {
    MemberDetail detail = new MemberDetail();
    detail.registeredAt = LocalDateTime.now();   // 생성에 따라오는 로직을 여기 모은다
    return detail;
}

void activate() {
    Assert.state(this.activatedAt == null, "이미 activatedAt은 설정되었습니다");
    this.activatedAt = LocalDateTime.now();
}
```

> 🟡 메서드 이름은 **값이 아니라 의도**로 짓는다. `setActivatedAt`은 "이 필드에 이 값을 넣어라"라고 외부가 지시하는 꼴이다. 활성화 시점에 시간 설정 말고 다른 작업이나 검증이 붙을 수 있으니 **`activate()`** 가 낫다. 이름을 한 번에 완벽히 지어야 한다는 생각은 버린다 — 의도를 더 잘 드러내는 쪽으로 바꿔 나가는 것이다.

### JPA 쪽에서 챙길 것

| 설정 | 이유 |
|---|---|
| `@OneToOne` 자체 | 🔴 없으면 JPA가 타입을 모른다는 에러를 낸다. 최소한 이 선언은 필요 |
| `cascade = ALL` | 🟡 **리포지토리는 루트 하나만** 만든다. 루트를 save하면 딸린 엔티티도 함께 영속화·삭제되어야 한다. 루트와 내부 엔티티 사이에는 모든 경우에 걸어 주는 게 좋다 |
| `fetch = LAZY` | 기본값 EAGER면 루트를 로딩할 때 무조건 내부까지 SELECT한다 |
| `@ToString.Exclude` | 🔴 `toString`이 연관 엔티티를 타고 가면 엄청난 수의 불필요한 SELECT가 일어난다 |

## 코드에 닿는 지점

**테스트도 루트를 통해서만.** 애플리케이션 기능을 Provided Interface로만 테스트하는 것과 같은 이유다.

cascade가 실제로 걸렸는지는 이렇게 확인한다 — `register` → `save` → **`flush + clear`로 영속성 컨텍스트를 비우고** → `findById`로 DB에서 다시 읽어 → 내부 엔티티의 값이 살아 있는지 본다.

🟢 이때 무엇을 검증할지 헷갈리기 쉽다. 방금 등록한 회원은 `PENDING`이므로 `activatedAt`은 **아직 null이 맞다.** 확인해야 하는 건 `registeredAt`이다.

## 트레이드오프

| 좁게 자를 때 | 넓게 자를 때 |
|---|---|
| 동시 수정 충돌이 줄고 락 범위가 좁다 | 불변식을 한 트랜잭션에서 지키기 쉽다 |
| 애그리거트 간 정합성을 이벤트로 맞춰야 한다 | 🔴 루트 하나에 버전이 걸리면 **내가 안 건드린 변경 때문에 충돌 판정**을 받는다 |

이 판단이 락 단위와 만나는 지점이 [[Coarse-Grained Lock]]이다.
