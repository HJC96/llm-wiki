## 한 줄 정의

> 🟡 **성공도 실패도 아닌 제3의 상태.** 외부 시스템이 처리했는지 알 수 없을 때 그것을 실패로 단정하지 않고 `UNKNOWN`으로 남겨, 나중에 조회해서 수렴시킬 여지를 남긴다.

## 왜 필요한가

PSP 승인 API가 타임아웃 났다. 이때 벌어졌을 수 있는 일은 셋이다.

1. 요청이 PSP에 도착하지 못했다 → 승인 안 됨
2. 승인은 됐는데 응답이 유실됐다 → **고객 카드는 이미 긁혔다**
3. PSP 내부에서 처리 중이다 → 곧 승인된다

> 🔴 **타임아웃을 `FAILURE`로 적는 순간 2번이 영영 사라진다.** 내부 원장에는 실패인데 PSP에는 승인이 남아 있고, 이 불일치는 월말 [[원장 대사]]에서야 발견된다. 반대로 `SUCCESS`로 적으면 1번에서 받지도 않은 돈을 정산한다.

## 어떻게 동작하는가

```
NOT_STARTED
    │ 승인 실행권 획득 (CAS)
    ▼
EXECUTING ──── 확정 승인 ────> SUCCESS
    ├───────── 확정 거절 ────> FAILURE
    └───────── 응답 불명 ────> UNKNOWN
                                 │ PSP 조회 API / 같은 키로 재호출
                                 ├──> SUCCESS
                                 ├──> FAILURE
                                 └──> UNKNOWN  (다음 주기에 다시)
```

핵심은 `UNKNOWN`이 **최종 상태가 아니라 작업 대기열**이라는 점이다. [[복구 워커]]가 이 상태를 주기적으로 긁어 PSP에 다시 묻는다.

**상태 머신 설계 원칙 넷** — ① 최종 상태에서 과거 상태로 돌아가지 않는다(`SUCCESS`를 `FAILURE`로 덮어쓰는 퇴행 금지). ② 확정 실패와 결과 불명을 구분한다. ③ 전이 조건을 DB `WHERE` 절에 넣는다([[조건부 상태 전이 선점]]). ④ 상태를 추가하면 복구 쿼리와 모니터링 쿼리도 같이 고친다.

> 🟢 오류 코드 분류가 이 상태의 입구를 결정한다. Toss의 `REJECT_ACCOUNT_PAYMENT`(확정 거절)는 `FAILURE`, `PROVIDER_ERROR`·5xx·타임아웃은 재시도 후보, `ALREADY_PROCESSED_PAYMENT`는 실패가 아니라 **기존 승인 결과를 조회해 내부 상태를 수렴시키라는 신호**다.

## 코드에 닿는 지점

```java
try {
    var result = pspClient.confirm(command);      // DB 트랜잭션 밖
    return result.isApproved() ? SUCCESS : FAILURE;
} catch (TimeoutException | ConnectException e) {
    return UNKNOWN;                                // ← 실패로 단정하지 않는다
}
```

재조회·재승인에는 **원래의 Idempotency Key를 그대로** 쓴다. 키를 새로 만들면 PSP가 별개 결제로 인식해 이중 청구가 된다.

## 트레이드오프

| 둘 필요가 있을 때 | 없어도 될 때 |
|---|---|
| 외부 호출의 결과가 **되돌릴 수 없는 부수효과**를 남길 때 (결제, 메일 발송, 재고 차감) | 순수 조회처럼 재시도가 무해할 때 |
| 그 외부 시스템에 **결과 조회 수단**이 있을 때 | 조회 API가 없으면 `UNKNOWN`은 그냥 수동 처리 큐가 된다 |

대가 — 상태가 하나 늘면 그 상태를 다루는 쿼리·화면·알림·복구 경로가 전부 늘어난다. `UNKNOWN` 체류 시간과 건수는 반드시 지표로 만들어야 하고, 안 그러면 조용히 쌓인다.
