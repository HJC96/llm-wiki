## 한 줄 정의

🟡 읽고-계산하고-쓰는 사이에 다른 트랜잭션이 끼어들어 **먼저 쓴 갱신이 덮이는** 것.

## 왜 필요한가

이 문제를 모르면 "락을 걸었는데 왜 값이 안 맞지?"에서 막힌다. 대개 **락의 단위가 문제와 어긋나 있다.**

주문 단위로 [[Redis 분산락]]을 걸어 뒀어도 키가 `orderId`라면, **서로 다른 주문이 같은 상품을 살 때는 아무것도 막히지 않는다.**

## 어떻게 동작하는가

```mermaid
sequenceDiagram
    participant O1 as 주문 1
    participant DB as product 로우
    participant O2 as 주문 2
    O1->>DB: SELECT (reserved=0)
    O2->>DB: SELECT (reserved=0)
    O1->>DB: UPDATE reserved=2
    O2->>DB: UPDATE reserved=5
    Note over DB: 최종 5. 주문 1의 예약 2개가 사라짐
```

🟢 예약 수량은 **7**이 되어야 하는데 **5**가 된다. 주문 2가 읽은 값(0)이 이미 낡았는데도 그 위에서 계산했기 때문이다.

## 코드에 닿는 지점

문제를 만드는 코드는 지극히 평범하게 생겼다.

```java
Product product = productRepository.findById(id).orElseThrow();  // 읽고
product.reserve(quantity);                                        // 계산하고
// 트랜잭션 커밋 시 UPDATE                                          // 쓴다
```

세 줄 사이에 다른 트랜잭션이 들어올 수 있다는 것이 전부다.

## 트레이드오프

푸는 길이 셋이다. 이건 트레이드오프라기보다 **선택 기준**이다.

| 방법 | 언제 |
|---|---|
| [[낙관적 락]] (`@Version`) | 충돌이 드묾. 재시도 로직을 붙일 수 있음 |
| [[비관적 락]] (`FOR UPDATE`) | 충돌이 잦음. 대기·데드락을 감수 |
| [[원자적 UPDATE로 푸는 동시성]] | 읽은 값이 계산에 필요 없을 때 (`SET x = x - 1`) |

🔴 **읽기 자체는 다른 트랜잭션의 읽기를 막지 않는다.** `SELECT`를 아무리 정교하게 짜도 이 틈은 안 없어진다. 쓰기 시점에 조건을 거는 것(버전 비교 또는 원자적 UPDATE)이 유일한 해법이다.

🔴 [[Saga 패턴]]에서 이력 테이블로 [[멱등성]]을 확보해도 Lost Update는 **그대로 남는다.** 이력 테이블은 "같은 요청이 두 번"을 막을 뿐, "다른 요청이 같은 로우를"은 못 막는다. 층이 다르다.

## 요청이 나뉘면 위 셋이 다 무력해진다

위 표의 세 해법은 전부 **읽기와 쓰기가 한 트랜잭션 안에 있을 때**의 이야기다. 화면 조회와 저장이 별도 요청이면 틈이 트랜잭션 바깥으로 나가 버려서, 그 구간에는 `@Version`도 `FOR UPDATE`도 걸려 있지 않다.

```
요청 A: GET  → (트랜잭션 열림·닫힘)   ← 여기서 값을 읽고
        ...   사람이 편집하는 시간 ...   ← 🔴 이 구간이 무방비
요청 B: PUT  → (트랜잭션 열림·닫힘)   ← 여기서 쓴다
```

Fowler는 이 상황의 lost update를 오프라인 동시성 문제로 따로 분류한다. 해법은 버전을 클라이언트가 들고 다니게 하거나([[Optimistic Offline Lock]]) 락 레코드를 남기는 것([[Pessimistic Offline Lock]])이다 → [[업무 트랜잭션과 시스템 트랜잭션]]

## 실험으로 확인한 것

🟢 [[선착순 쿠폰 발급 동시성]]의 "동시성 제어 없음" 케이스가 이걸 그대로 재현한다 — 두 요청이 `quantity = 200`을 함께 읽고 각각 199를 써서 **최종 재고가 198이 아니라 199**가 된다.

🟢 [[TCC 실험]]은 이 문제를 **명시적으로 범위 밖에 뒀다.** 원저자 주: *"이건 TCC의 문제가 아니라 읽고-고쳐-쓰기의 문제라 별개로 다뤄야 한다."* 분산 트랜잭션 기법을 아무리 잘 짜도 이 층은 따로 막아야 한다는 뜻이다.
