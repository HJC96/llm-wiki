## 한 줄 정의

> 🟡 **도메인의 핵심 개념 · 관계 · 규칙만 남긴 추상화.** 지도가 땅의 전부가 아니듯, 목적에 필요한 것만 남긴 것이다.

**도메인**은 소프트웨어가 적용되는 특정한 주제 영역(문제 영역, Problem Domain)이다. 원래 뜻은 영토·소유지였고, 의미가 확장돼 지식·활동의 영역을 가리키게 됐다.

## 왜 필요한가

도메인은 현실이라 디테일이 많고 복잡하고 자주 변한다. 그 전체를 코드로 옮길 수 없으니 중요하지 않은 걸 걷어낸다.

> 🔴 "오늘은 화면 하나, 내일은 DB 넣고 빼는 기능" 식으로만 일이 내려오면 개발자는 **자기가 무엇을 만드는지 모른다.** 어떤 도메인이고 그게 어떻게 돌아가는지를 먼저 이해하는 게 개발의 출발점이다.

## 어떻게 동작하는가

담기는 것은 셋이다.

| | 무엇 |
|---|---|
| **개념** | 도메인에 존재하는 중요한 것들 (대체로 보통명사) |
| **관계** | 개념들이 서로 어떻게 이어지는가 |
| **규칙** | 그 도메인이 지키는 제약과 계산 |

```
온라인 서점
  개념 : 책, 고객, 주문, 장바구니
  관계 : 고객은 책을 주문한다 / 주문은 장바구니에 담긴 것으로 만들어진다
  규칙 : 장바구니에 담긴 상품의 가격과 수량으로 총액을 계산한다
```

> 🔴 **도메인 모델의 실체는 다이어그램이나 문서가 아니다.** 그건 공유하려고 꺼내 놓은 표현 수단일 뿐이고, 도메인 모델은 그것을 만들고 이야기하는 **팀 사람들 머릿속의 멘탈 모델**이다.

그래도 표현해 둔 것은 유용하다 — 새로 합류한 사람이 빠르게 파악하고, 잊힌 것을 되짚고, 갱신을 제안할 수 있다. 프로젝트에 남기는 셋: **용어 사전**(한국어 ↔ 영어 ↔ 정의), **도메인 모델 기술서**(사람의 언어로), **다이어그램**(관계처럼 눈으로 봐야 직관적인 것).

> 🟢 다만 **개발자에게 도메인 모델의 최종 표현은 코드**다. 코드를 보면서 도메인 모델을 읽을 수 있어야 하고, 텍스트 기록은 그걸 대체하는 게 아니라 보조한다.

## 코드에 닿는 지점

문서로 정리한 모델과 실제 `Member` 클래스를 각각 다이어그램으로 그렸을 때 거의 일치하면, **표현적 차이(representational gap)** 가 작은 것이다. 그게 목표다.

## 트레이드오프

| 모델을 명시적으로 관리할 때 | 안 할 때 |
|---|---|
| 도메인이 복잡하거나 오래 갈 때 | 단발성 스크립트, CRUD만 있는 관리 화면 |
| 여러 사람이 같은 용어로 이야기해야 할 때 | 혼자 짧게 만들고 버릴 때 |
