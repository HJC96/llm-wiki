## 한 줄 정의

🟡 낙관적 락은 충돌을 **막는** 장치가 아니라 **감지하는** 장치다. 아무것도 잠그지 않고 버전만 비교한다.

> "락"이라는 말이 층위가 다른 셋을 가리킨다 — DB가 로우에 거는 락([[비관적 락]]), Redis에 키를 쓰는 애플리케이션 락([[Redis 분산락]]), 그리고 **아무것도 잠그지 않는** 낙관적 락. 이름만 같다.

## 왜 필요한가

주문 단위 락은 이미 걸어 뒀다. 하지만 그 락의 키는 `orderId`다. **서로 다른 주문이 같은 상품을 살 때는 아무것도 막히지 않는다.** → [[Lost Update]]

## 어떻게 동작하는가

버전 컬럼을 두고, UPDATE할 때 **읽어 온 버전과 지금 DB의 버전이 같을 때만** 반영한다. 주문 1이 버전 0 → 1로 올려 놓았으면 버전 0을 들고 온 주문 2의 UPDATE는 0건 갱신으로 실패한다. 실패하면 다시 읽어서 처음부터 계산한다.

## 코드에 닿는 지점

```java
@Entity
public class Product {
    @Version                      // ← JPA가 UPDATE에 version 조건과 증가를 자동으로 붙인다
    private Long version;
}
```

**재시도를 어디에 둘 것인가가 실제 설계다.**

```java
@Component
public class ProductFacadeService {
    public ProductReserveResult tryReserve(ProductReserveCommand command) {
        int tryCount = 0;
        while (tryCount < 3) {                                    // 3번까지만
            try {
                return productService.tryReserve(command);        // ← @Transactional은 이 안쪽
            } catch (ObjectOptimisticLockingFailureException e) { // 낙관적 락 충돌만 재시도
                tryCount++;
            }
        }
        throw new IllegalStateException("예약 재시도 초과");
    }
}
```

🟢 재시도를 서비스가 아니라 **Facade에 둔 이유** — `ObjectOptimisticLockingFailureException`은 **flush/commit 시점에** 터진다. 같은 트랜잭션 안에서 잡아 재시도해 봐야 그 트랜잭션은 이미 되돌릴 수 없는 상태다. **트랜잭션을 완전히 닫고 새로 열어야 재시도가 성립한다.** Facade는 그 경계를 만드는 장치다.

💬 이 지점이 면접에서 "실제로 써 본 사람"을 가른다.

## 한 트랜잭션을 넘어가면

🟡 이 페이지가 설명하는 것은 **하나의 시스템 트랜잭션 안**에서 벌어지는 일이다. `@Version`이 버전을 들고 있는 건 영속성 컨텍스트가 살아 있는 동안뿐이라, 조회와 저장이 **다른 요청**이면 그 사이는 아무것도 지켜 주지 않는다.

같은 알고리즘을 업무 트랜잭션 전체로 확장하려면 버전을 응답에 실어 내보내고 저장 요청에서 되받아야 한다. Fowler는 이 형태를 [[Optimistic Offline Lock]]이라는 별도 패턴으로 부른다 → [[업무 트랜잭션과 시스템 트랜잭션]]

## 트레이드오프

| 낙관적 | 비관적 |
|---|---|
| 충돌을 **감지** | 충돌을 **차단** |
| 락 비용 0, 대신 **재시도 필요** | `SELECT … FOR UPDATE`, 대신 대기·데드락 |
| 충돌이 **드물 때** | 충돌이 **잦을 때** |

🟡 감지 이후 무엇을 할지(재시도할지, 포기할지)는 애플리케이션이 정해야 한다. **재시도 로직이 없으면 낙관적 락은 그냥 실패율만 높인다.**

🔴 재시도 횟수를 무제한으로 두면, 경합이 심한 인기 상품에서 스레드가 재시도만 반복하며 커넥션을 붙들어 **서비스 전체를 끌어내린다.** 3회 같은 상한은 관례가 아니라 안전장치다.

🔴 재고처럼 **항상** 경합하는 데이터라면 낙관적 락으로는 실패율이 너무 높다. 비관적 락이나 Redis 기반 카운터·큐 직렬화 같은 다른 층의 해법으로 넘어간다.

💬 `@Version`을 붙이는 것만으로는 **아무 문제도 해결되지 않는다.** 예외가 터지기 시작할 뿐이고, 그 예외를 어떻게 처리할지가 실제 설계다.

## 실험으로 확인한 것

🟢 [[선착순 쿠폰 발급 동시성]]에서 200 요청이 한 로우를 다투자 **낙관적 락이 9가지 중 가장 느렸다.**

| 낙관적 락(재시도) | 비관적 락 | 원자적 UPDATE |
|---|---|---|
| **3156ms** | 429ms | 369ms |

🔴 "충돌이 드물 때만"이라는 전제가 빈말이 아니다. 경합이 상시적이면 **재시도가 반복되며 7~9배 느려진다.**
