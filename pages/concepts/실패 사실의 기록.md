## 한 줄 정의

🟡 분산 트랜잭션 설계의 마지막 층은 **"실패했다는 사실을 유실하지 않는 것"**이다. 자동으로 복구하지 못하더라도, **복구가 필요하다는 사실이 조회 가능한 데이터로** 남아 있으면 사람이든 배치든 나중에 처리할 수 있다.

## 왜 필요한가

재고를 차감하고 포인트를 차감한다. 도중에 에러가 나면 보상 트랜잭션으로 되돌린다. **그런데 롤백 도중에 에러가 나면?**

기록이 없으면 주문 상태를 보고 유추하는 수밖에 없다. 주문이 `REQUESTED`에 멈춰 있다는 사실만 남고, **어디까지 되돌아갔는지는 알 수 없다.**

🟢 실제로 취소 로직에 강제 예외를 넣고 테스트하면 이렇게 남는다 — 포인트는 사용조차 안 됐고, 재고는 롤백되지 않은 채 취소 기록도 없으며, 주문은 `REQUESTED`에 멈춰 있다. **`CompensationRegistry`에 쌓인 그 한 행이 없으면 이 상태를 발견할 방법이 없다.**

## 어떻게 동작하는가

실패 자체를 데이터로 남긴다.

```java
@Entity
public class CompensationRegistry {
    @Id @GeneratedValue private Long id;
    private Long orderId;
    @Enumerated(EnumType.STRING)
    private Status status;       // PENDING / COMPLETE

    public CompensationRegistry(Long orderId) {
        this.orderId = orderId;
        this.status = Status.PENDING;   // ← 보상 실패 시점에 기록
    }
}
```

코디네이터의 `catch` 블록 안에서 보상 호출이 **또** 예외를 던지면 이 레코드를 저장한다. 배치가 주기적으로 `PENDING` 행을 조회해 보상을 재요청하고, 성공하면 `COMPLETE`로 바꾼다.

> ⚠️ 이름 충돌 주의. 이 `PENDING`은 [[TCC]]의 주문 상태 `PENDING`과 **다르다.** 저쪽은 확정에 실패한 주문, 이쪽은 보상에 실패한 기록. 공교롭게도 둘 다 "나중에 사람이나 배치가 처리해야 할 일"을 뜻한다는 점만 같다.

## 코드에 닿는 지점

세 개의 안전망이 생기고, 셋 다 **운영 지표**가 된다.

| 지표 | 무엇을 알려주나 |
|---|---|
| `PENDING` 주문 수 | [[TCC]] 확정 실패 잔여 |
| 오래 `RESERVED`인 예약 수 | 취소가 도달 못 한 자원 |
| `CompensationRegistry`의 `PENDING` 행 수 | [[Saga 패턴]] 보상 실패 |
| Redis 락 키가 TTL 없이 남은 수 | [[Redis 분산락]] 해제 실패 |
| `ObjectOptimisticLockingFailureException` 발생률 | [[낙관적 락]] 경합 강도 |
| 컨슈머 랙 | Choreography에서 미처리 주문의 양 |

🟡 **이 셋은 0이어야 정상이 아니라, 감시되고 있어야 정상이다.**

## 트레이드오프

🔴 **재시도 배치가 호출하는 것도 결국 같은 취소 API다.** 그 API가 [[멱등성]]을 갖추지 않으면 배치가 돌 때마다 재고가 계속 늘어난다. 이력 테이블이 여기서 다시 방어선이 된다.

🔴 **자동 해소가 항상 옳지 않다.** [[TCC]]의 `PENDING` 주문을 자동 확정하면 고객이 재주문해 정상 완료한 경우 **같은 물건을 두 번 산 결과**가 된다.

판단 기준은 **판단의 여지가 있는가**다.

| | 자동화 | 사람 |
|---|---|---|
| 취소 | ✅ "주문이 이미 취소됨"이라는 사실 하나로 판정 끝 | |
| 확정 | | ✅ 되돌릴 수 없고 비즈니스 맥락에 따라 답이 달라짐 |

이런 사례가 반복 누적된 다음에야 그 비즈니스에 맞는 자동화를 설계하는 것이 순서다.
