## 한 줄 정의

> 🟡 **한 번의 논리적 작업이 서로 다른 두 시스템에 써야 하는데, 그 둘을 하나의 트랜잭션으로 묶을 방법이 없는 상태.**

## 왜 필요한가

이름을 붙여야 해법을 고를 수 있기 때문이다. "Kafka 발행이 가끔 안 된다"는 버그 리포트처럼 들리지만, Dual Write라고 부르는 순간 그건 버그가 아니라 **구조상 반드시 존재하는 창(window)** 이 된다. 코드를 아무리 조심히 써도 두 write 사이에서 프로세스는 죽을 수 있다.

전형적인 조합 — DB + 메시지 브로커, DB + 외부 API, DB + 캐시, DB + 검색 인덱스.

## 어떻게 동작하는가

```
       write A ──┐
                 ├── 이 사이에서 죽으면 A만 남는다
       write B ──┘
```

순서를 바꿔도 문제는 이동할 뿐 사라지지 않는다.

| 선택 | 남는 사고 |
|---|---|
| DB 먼저 | DB엔 있는데 이벤트가 안 나감 → **유실** |
| 브로커 먼저 | 이벤트는 퍼졌는데 DB가 롤백 → **불일치** |
| 2PC로 묶기 | 코디네이터 장애 시 [[2PC]]의 블로킹. 브로커가 XA를 지원해야 한다 |

> 🔴 "트랜잭션 안에서 Kafka로 쏘면 롤백될 때 같이 취소되지 않나" — 안 된다. `@Transactional`은 커넥션 하나의 트랜잭션만 연다([[분산 트랜잭션이 필요한 순간]]). 이미 브로커로 나간 바이트를 되돌릴 방법은 없다.

**실용적인 해법의 방향은 하나다** — 두 시스템 쓰기를 **한 시스템 쓰기 + 나중에 전달**로 바꾼다. 그게 [[Outbox 패턴]]이고, 전달이 여러 번 일어나는 것은 [[멱등성]]으로 받는다.

## 코드에 닿는 지점

```java
@Transactional
public void confirm(...) {
    paymentRepository.updateStatus(SUCCESS);   // 시스템 1
    kafkaTemplate.send("payment-approved", e); // 시스템 2 — 여기가 Dual Write
}
```

## 트레이드오프

| 그냥 두어도 될 때 | 반드시 풀어야 할 때 |
|---|---|
| 두 번째 write가 유실돼도 비즈니스가 안 깨지는 경우 (조회 캐시 워밍, 통계) | 금전 상태 변경, 재고 차감, 정산 — 한쪽만 남으면 돈이 틀어진다 |
| 재구축 수단이 따로 있는 경우 (검색 인덱스 전체 재색인 배치) | 재구축할 원천이 없는 경우 |
