## 한 줄 정의

🟡 재시도는 실패를 줄이는 장치가 아니라 **실패를 반복하는 장치**다. [[멱등성]] 위에서만 안전하다.

## 왜 필요한가

MSA에서 네트워크 오류와 일시적 장애는 상시 전제다. 커넥션 풀 부족, 순간적 단절, 상대 서버의 일시적 DB 커넥션 고갈.

이런 일시적 실패에 곧바로 보상 트랜잭션을 발행하는 것은 **과하다.** 재시도로 극복하는 편이 신뢰성을 높이고 불필요한 보상 비용을 줄인다.

가장 까다로운 것은 **타임아웃**이다. 타임아웃이 났더라도 상대는 요청을 정상 처리했을 수 있다 — [[분산 트랜잭션이 필요한 순간]]의 "알 수 없음" 상태.

## 코드에 닿는 지점

```java
@Retryable(
    retryFor = Exception.class,
    noRetryFor = {                                    // 재시도해도 결과가 같은 예외는 제외
        HttpClientErrorException.BadRequest.class,    // 400
        HttpClientErrorException.NotFound.class       // 404
    },
    maxAttempts = 3,                                  // 무제한 금지
    backoff = @Backoff(delay = 200)                   // 즉시 재시도는 또 실패하기 쉽다
)
public PointReserveResponse reserve(PointReserveRequest request) { ... }
```

*Spring Boot 3.x / Spring Retry 2.x 기준. 애플리케이션 클래스에 `@EnableRetry` 필요.*

읽기 타임아웃도 함께 잡는다.

```java
var factory = new SimpleClientHttpRequestFactory();
factory.setReadTimeout(Duration.ofSeconds(2));        // 응답이 2초를 넘으면 끊는다
```

*`setReadTimeout(Duration)` 오버로드는 Spring Framework 6.1(Boot 3.2) 이상. 이전엔 밀리초 `int`.*

🟢 모든 장치가 한 장면에서 맞물리는 로그가 이렇다. **1차** — 진입은 했지만 2초 초과로 타임아웃. **2차(재시도)** — 1차가 아직 처리 중이라 [[Redis 분산락]] 획득 실패. **3차(재시도)** — 1차가 끝났고 상태 검사가 "이미 예약된 요청"을 감지해 저장된 응답을 반환. **최종 성공, 예약은 정확히 한 건.**

## 트레이드오프

🔴 **모든 오류를 재시도하면 안 된다.** 400·404는 몇 번을 다시 보내도 같은 답이 오고, 그 사이 호출자의 스레드와 커넥션만 묶인다.

🔴 `@Retryable`은 `@Transactional`과 **같은 프록시 기반**이라 같은 클래스 안에서 자기 메서드를 호출하면 동작하지 않는다.

🔴 상대 서버가 죽어 있으면 재시도가 오히려 **장애 중인 상대에게 부하를 더 얹는다.** 여기서 서킷 브레이커로 넘어간다.

🔴 타임아웃 없는 재시도는 스레드만 묶는다. 둘은 함께 설계해야 한다.

💬 "`@Retryable` 붙이고 3번 재시도합니다"는 설정값만 말한 것이다. **왜 3번인지, 멱등성이 왜 전제인지**를 붙여야 한다.
