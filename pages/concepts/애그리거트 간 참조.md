## 한 줄 정의

다른 애그리거트를 **객체로 들고 있어도 된다.** 갈리는 건 참조 방식이 아니라 **그것으로 무엇을 하느냐**다. 조회는 되고 변경은 안 된다.

## 왜 필요한가

"애그리거트끼리는 ID로만 참조해야 한다"는 말을 자주 듣는다. 🔴 **이 강의의 선택은 다르다.**

```text
직접 참조로 시작한다 → 필요해지면 식별자 참조로 전환한다
```

직접 참조한다고 두 애그리거트가 하나로 합쳐지는 게 아니다. 경계는 **참조 방식이 아니라 변경 책임**으로 정해진다.

## 어떻게 동작하는가

### 조회는 허용, 변경은 금지

🟢 **팀 개발가이드의 문장 그대로다.**

> 애그리거트는 다른 애그리거트 루트를 직접 참조할 수 있다. 조회 메소드(getter 등)와 레코드 메서드 사용 가능. 단, 다른 애그리거트를 변경하는 메서드는 사용할 수 없다.
>
> 애플리케이션 서비스는 다른 애플리케이션 서비스의 기능 제공(provided) 포트의 인터페이스와 DTO를 사용할 수 있다. 단, 구현 클래스는 직접 액세스하지 않는다.

| 다른 애그리거트에 대해 | |
|---|---|
| getter · `isXXX` · record accessor | ✅ |
| 상태 변경 메서드 호출 | 🔴 금지 |

🟡 **다른 애그리거트의 상태까지 자유롭게 바꾸면 변경 책임이 흩어지고, 그 순간 경계는 그림일 뿐이 된다.** 불변식을 누가 지키는지 알 수 없어진다 → [[애그리거트 경계 정하기]]

### 그럼 다른 애그리거트를 바꿔야 할 땐?

엔티티 안에서 따라가서 바꾸지 않는다. **애플리케이션 서비스가 담당 컴포넌트의 제공 인터페이스를 호출한다.**

```text
엔티티 내부에서 직접 변경     🔴
애플리케이션 서비스가 요청    ✅
```

이때 컴포넌트 간 순환 의존은 금지된다 → [[모듈 간 순환 의존]]

### 🟡 객체를 갖고 있는데 왜 ID를 넘기나

여기가 반직관적인 지점이다. 직접 참조로 `Curriculum` 객체를 이미 들고 있는데도 변경 요청에는 `courseId`를 넘긴다.

**같은 제공 인터페이스를 외부 어댑터와 내부 컴포넌트가 함께 쓰기 때문이다.**

```text
웹 어댑터    →  courseId만 갖고 있다 (HTTP 요청에서 옴)
내부 컴포넌트 →  객체를 갖고 있다
                 ↓
        둘 다 같은 제공 인터페이스를 호출한다
                 ↓
        계약을 식별자 기반으로 맞춘다
```

외부 요청은 어차피 식별자로 들어온다. 인터페이스를 객체 기반으로 만들면 어댑터가 먼저 조회해야 하고, 계약이 둘로 갈라진다.

🔴 **부수 효과가 하나 더 있다.** 계약에 도메인 타입이 안 나타나므로 그 타입에 대한 의존이 생기지 않는다. [[모듈 간 순환 의존]]의 "반환 타입으로 의존이 되살아난다"와 같은 축이다.

## 트레이드오프

| | 직접 참조 | 식별자 참조 |
|---|---|---|
| 읽기 편의 | 그래프를 따라간다 | 매번 조회한다 |
| 경계 | 🔴 실수로 변경하기 쉽다 | 애초에 못 바꾼다 |
| 로딩 | LAZY·N+1을 신경 써야 한다 | 필요한 것만 |
| 전환 비용 | — | 나중에 바꾸면 호출부가 다 바뀐다 |

- 🔴 **"처음부터 ID 참조"가 항상 옳은 건 아니다.** 경계가 아직 확정되지 않았는데 ID로 끊어 두면, 나중에 같은 애그리거트였다는 게 드러났을 때 되돌리기가 더 비싸다
- **직접 참조를 택했다면 규칙이 문서에만 있으면 안 된다.** 사람 눈으로는 getter 호출과 변경 호출을 계속 구분하기 어렵다 → [[Slice와 Layer]]의 커스텀 `ArchCondition`
- 🔴 이 소스는 **언제 전환할지의 기준**을 주지 않는다. "필요하면"이라고만 한다
