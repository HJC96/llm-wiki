## 한 줄 정의

🟡 충돌을 **감지**하는 [[낙관적 락]]과 달리, 읽는 시점에 락을 걸어 **충돌 자체를 차단**한다.

## 왜 필요한가

[[Lost Update]]를 막는 세 길 중 하나다. 낙관적 락은 충돌이 잦으면 재시도만 반복하다 스레드를 태운다 — 🟢 실험에서 200 요청이 한 로우를 다투자 낙관적 락이 **3156ms**로 비관적 락(**429ms**)보다 7배 느렸다.

경합이 상시적인 데이터(인기 상품 재고, 선착순 쿠폰)에서는 "감지 후 재시도"보다 "줄 세우기"가 싸다.

## 어떻게 동작하는가

읽을 때 배타 락을 잡고, 트랜잭션이 끝날 때까지 다른 트랜잭션의 같은 행 접근을 막는다.

```sql
SELECT * FROM coupon WHERE id = 1 FOR UPDATE;   -- 여기서 락 획득
UPDATE coupon SET quantity = quantity - 1 WHERE id = 1;
COMMIT;                                          -- 여기서 해제
```

읽고-계산하고-쓰는 구간 전체가 보호되므로 중간에 끼어들 틈이 없다.

## 코드에 닿는 지점

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select c from Coupon c where c.id = :id")
Optional<Coupon> findByIdForUpdate(@Param("id") Long id);
```

JPA는 `LockModeType.PESSIMISTIC_WRITE`를 `FOR UPDATE`로 번역한다.

## 트레이드오프

| 쓸 때 | 안 쓸 때 |
|---|---|
| 충돌이 **잦다** (인기 상품, 선착순) | 충돌이 드물다 → [[낙관적 락]] |
| 재시도 로직을 짜기 싫다 | 읽은 값이 계산에 필요 없다 → [[원자적 UPDATE로 푸는 동시성]] |
| 락 대기 시간을 감당할 수 있다 | 여러 인스턴스가 서로 다른 DB를 본다 → [[Redis 분산락]] |

🔴 **락을 쥐는 시간이 곧 다른 요청의 대기 시간이다.** 락 구간 안에서 외부 API를 호출하면 그 응답 시간만큼 전체가 막힌다.

🔴 **데드락이 생긴다.** 여러 행을 락 거는 순서가 트랜잭션마다 다르면 서로를 기다린다. 접근 순서를 고정하는 것이 기본 처방이다.

🔴 **갭 락에 주의.** MySQL InnoDB는 REPEATABLE READ에서 인덱스 범위에 갭 락을 함께 건다. 인덱스를 안 타는 조건으로 `FOR UPDATE`를 걸면 훨씬 넓은 범위가 잠긴다 → [[갭 락과 넥스트키 락]]

🟢 [[2PC 실험]]의 `ERROR 1205 Lock wait timeout exceeded`가 이 대기의 극단적 형태다 — 거기선 코디네이터가 결정을 줄 때까지 락이 안 풀린다.

## 이름이 같은 다른 패턴과 헷갈리지 않기

🟡 **이 락은 트랜잭션에 종속된다.** 커밋·롤백하는 순간 자동으로 풀리므로, "화면을 열어 둔 5분 동안 잠가 둔다" 같은 건 애초에 불가능하다. 그 구간을 덮으려면 수명이 트랜잭션보다 긴 락이 필요하다.

| | 수명 | 이 구간을 덮나 |
|---|---|---|
| 비관적 락 (`FOR UPDATE`) | 트랜잭션 | ❌ |
| [[네임드 락]] (`GET_LOCK`) | 세션 | ✅ |
| [[Pessimistic Offline Lock]] | 업무 트랜잭션 (락 테이블) | ✅ |

이름이 닮은 [[Pessimistic Offline Lock]]은 DB 행 락이 아니라 **별도 테이블의 락 레코드**로 구현되는 상위 패턴이다.
