## 한 줄 정의

🔴 **한 서버에서 `@CacheEvict`를 실행해도 다른 서버의 로컬 캐시는 그대로다.** WAS가 2대가 되는 순간 무효화가 반쪽이 된다.

## 왜 필요한가

로컬 캐시는 싸다 — 네트워크 왕복도, 직렬화도, 별도 인프라도 없다. 그래서 초기 인프라에 Redis가 없을 때 자연스러운 첫 선택이 된다.

문제는 **스케일아웃하는 순간**이다. 인스턴스마다 자기 메모리에 자기 사본을 들고 있고, 무효화 신호는 자기 프로세스 밖으로 나가지 않는다.

## 어떻게 동작하는가

무효화를 **전파**할 수 없다면, 무효화 자체를 없애는 방법이 있다 — **키를 바꿔 세대를 넘긴다.**

```java
// {max(updatedAt), id} 를 키로 사용
findBookNameByIdWithTableVersion(long id)
```

공통 테이블의 `max(updatedAt)`을 **테이블 버전처럼 키에 포함**한다. 어떤 row가 바뀌든 새 버전 키가 되므로 모든 인스턴스에서 자연스럽게 miss가 나고, **기존 캐시를 지우지 않고도 캐시 세대 전체가 넘어간다.**

🟢 실무 조건 — `max(updated_at)` 조회가 가벼워야 하므로 `updated_at` 인덱스가 필요하다. 공통코드 그룹처럼 구분 컬럼이 있으면 `(group_key, updated_at)` 복합 인덱스를 고려한다.

## 코드에 닿는 지점

이 기법이 잘 맞는 데이터는 **변경 빈도가 낮고 여러 화면에서 반복 조회되는 것** — 공통코드, 메뉴, 설정값. 반대로 자주 바뀌는 데이터에 쓰면 버전이 계속 올라가 캐시가 무의미해진다.

## 트레이드오프

| 로컬 캐시 유지 | 공용 캐시로 이동 |
|---|---|
| 인프라 추가 없음, 왕복 없음 | 인스턴스 간 정합성이 공짜 |
| 저빈도 변경 데이터 | 무효화를 즉시 전파해야 함 |
| 테이블 버전 키로 우회 가능 | 캐시 서버 장애가 새 실패 지점 |

🔴 **옛 세대 키가 메모리에 남는다.** 테이블 버전 키는 지우지 않고 넘어가는 방식이라 TTL이나 최대 크기가 반드시 함께 있어야 한다.

🔴 **서버 재시작 시 캐시가 사라진다.** 로컬 캐시의 기본 성질이고, 기동 직후 [[Cache Stampede]]가 나기 쉬운 구간이 된다.

🔴 **버전 조회가 매 요청에 추가된다.** `max(updated_at)` 쿼리가 가볍지 않으면 캐시로 아낀 것을 도로 쓴다.

💬 실무에서 로컬 캐시를 고른 판단(초기 인프라에 Redis가 없고 공통코드는 저빈도 변경 데이터였다)과, 그때 남겨 둔 숙제(WAS 2대 이상이면 정합성 이슈)가 정확히 이 페이지의 내용이다.

### 다른 길 — 인스턴스마다 직접 무효화한다

테이블 버전 키가 "옛 값을 안 보게 만드는" 방식이라면, 반대쪽 길은 **관리 엔드포인트로 각 인스턴스의 캐시를 직접 지우는 것**이다. Spring Boot Actuator의 `DELETE /actuator/caches/{name}`이 그 수단이다.

> 🔴 **L7 로드밸런서를 통해 호출하면 어느 인스턴스가 받을지 보장되지 않는다.** 한 번 호출로 지워졌다고 믿으면 나머지 인스턴스는 옛 값을 계속 준다. 각 서버에 접속해 `localhost`로 호출해야 대상이 확정된다.

> 🔴 그리고 이 엔드포인트가 외부에 노출되면 **누구나 캐시를 날릴 수 있다.** 노출 제어·인증·네트워크 경계가 함께 필요하다 → [[Actuator 엔드포인트 보안 경계]]

| | 테이블 버전 키 | 관리 엔드포인트 무효화 |
|---|---|---|
| 전파 | 자동 (다음 조회부터) | 수동. 인스턴스마다 호출 |
| 비용 | 매 요청에 버전 조회 | 평상시 0 |
| 남는 문제 | 옛 세대 키가 메모리에 잔존 | **운영 절차가 사람에게 남는다** — 문서화 안 되면 만든 사람만 안다 |
