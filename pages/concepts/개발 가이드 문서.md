## 한 줄 정의

팀의 설계 규칙을 **한 파일에 명시적으로 적어 두는 것**. 리뷰·온보딩·아키텍처 테스트·AI 코딩이 같은 문서를 기준으로 삼는다.

## 왜 필요한가

설계 규칙은 대개 세 군데에 흩어져 산다.

```text
사람 기억 속       "원래 그렇게 해 왔는데"
코드리뷰 코멘트     매번 다시 설명한다
아키텍처 테스트     기계가 읽을 수 있는 것만
```

🔴 **세 군데 중 어디도 "왜 그런지"를 남기지 않는다.** 테스트는 위반을 잡지만 이유를 말하지 않고, 리뷰 코멘트는 PR이 닫히면 사라진다.

🟡 **AI 코딩이 들어오면서 이게 더 중요해졌다.** AI는 매번 그럴듯하지만 조금씩 다른 스타일로 코드를 만든다. 팀 규칙을 문서로 주면 그게 **제약(harness)** 이 된다. 이 볼트의 `CLAUDE.md`가 정확히 그 역할을 한다.

## 어떻게 동작하는가

실제 가이드가 다루는 항목은 대략 이렇다.

| 절 | 무엇을 고정하나 |
|---|---|
| 기술 스택 | 버전까지 명시 (Java 21, Boot 3.5.x) |
| 아키텍처 | 의존성 방향 한 문장 + **위반 시 빌드 실패**라고 못 박음 |
| 패키지 | 트리를 그대로 그려 둔다 |
| 애그리거트 의존관계 | Slice 정의, 참조 허용 범위 |
| 포트 패턴 | provided / required 구분과 예시 이름 |
| 도메인 모델 관례 | setter 금지, 정적 팩터리, 불변식 검증 위치 |
| 서비스 관례 | 애노테이션 묶음, 조회/변경 분리 |
| 테스트 관례 | 픽스처 위치, 어떤 테스트를 어디에 |
| 네이밍 | 포트·서비스·예외 이름 규칙 |

🟡 **좋은 항목은 "무엇을 하라"가 아니라 "무엇을 하지 마라"가 붙어 있다.**

```text
상태 변경은 의미 있는 도메인 메서드로만. setter 금지
다른 애그리거트를 변경하는 메서드는 사용할 수 없다
구현 클래스는 직접 액세스하지 않는다
도메인은 웹 DTO를 직접 받지 않는다
```

금지 항목이 없는 가이드는 읽고 나서도 판단이 안 선다.

### 문서와 테스트가 짝을 이룬다

가이드에 적힌 것 중 **기계가 판별할 수 있는 것**은 테스트로 내린다.

```text
문서: "의존성 방향은 안쪽으로만"
  ↓
테스트: HexagonalArchitectureTest → 위반 시 빌드 실패
```

🔴 **둘 중 하나만 있으면 새어 나간다.** 문서만 있으면 아무도 안 지키고, 테스트만 있으면 왜 막혔는지 모른 채 우회 방법을 찾는다 → [[ArchUnit으로 아키텍처 강제하기]] · [[Slice와 Layer]]

### 용어 사전이 붙는다

같은 저장소에 **한국어 / 영어 / 설명** 세 칸짜리 표가 따로 있다.

| 한국어 | 영어 | 설명 |
|---|---|---|
| 수강 | Enrollment | 회원이 강의를 학습하는 것 |
| 섹션 | Section | 강의를 세부 주제별로 나눈 중간 단위 |

🟡 **이게 [[보편 언어]]의 실물이다.** 개념이 아니라 표 한 장으로 존재하고, 클래스 이름이 그 표의 영어 칸과 같다.

## 트레이드오프

- 🔴 **가장 큰 위험은 문서가 코드보다 뒤처지는 것이다.** 낡은 가이드는 없는 것보다 나쁘다. 사람이 "이건 옛날 규칙"이라고 판단해야 하므로 가이드 전체의 신뢰가 떨어진다
- **그래서 기계로 강제 가능한 항목부터 테스트로 내린다.** 테스트는 코드와 함께 깨지므로 뒤처지지 않는다. 문서에는 **판단이 필요한 것**만 남긴다
- 🔴 **너무 자세하면 아무도 안 읽는다.** 위 가이드가 94줄인 건 우연이 아니다. 항목마다 한두 줄이고 예시는 이름 하나뿐이다
- **AI에게 주는 용도라면 형식이 중요해진다.** 산문보다 목록과 표가 낫고, 금지 항목이 명시돼 있어야 한다
