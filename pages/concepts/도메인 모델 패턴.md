## 한 줄 정의

> 🟡 **도메인을 객체 모델로 표현하는 방식.** 속성과 그 속성을 다루는 로직이 한 객체 안에 함께 있다. 반대편은 트랜잭션 스크립트다.

출처는 마틴 파울러 『Patterns of Enterprise Application Architecture』(PoEAA, 2002).

## 왜 필요한가

상태를 꺼내서 바깥에서 비교하고 바꾸는 코드가 쌓이면, 같은 판단이 온갖 곳에 중복되고 **"이 데이터가 대체 어디서 바뀐 거지?"** 가 시작된다(진도 체크하는 코드에서 세터를 호출했더라, 같은 일). 회원이라는 도메인의 관심사가 **한 곳에 모이게** 하는 것이 목적이다.

## 어떻게 동작하는가

### 두 가지 스타일

| | 단순 도메인 모델 | 풍성한 도메인 모델 |
|---|---|---|
| 구조 | 테이블 하나당 도메인 클래스 하나 | DB 테이블과 1:1이 아니다 |
| 기법 | — | 다형성을 위한 상속, 전략 패턴(도메인 서비스 주입), 엔티티·값 객체가 **직접 레퍼런스로 연관** |
| DB 매핑 | 쉽다 | 🔴 어렵다. 클래스 4~5개가 테이블 하나에 대응하거나 상속을 매핑해야 한다 |

> 🟡 **단순 도메인 모델이 나쁜 게 아니다.** DB 입출력용 데이터만 갖는 게 아니라 **그 데이터를 다루는 로직까지 갖고 있으면** 이것도 어엿한 도메인 모델이다. 도메인이 복잡하지 않으면 여기서 시작해도 된다.

> 🔴 **애니믹(빈혈) 도메인 모델** — 속성만 있고 기능이 없는 것. 생긴 건 DB 테이블과 똑같고 로직은 전부 바깥 서비스에 트랜잭션 스크립트로 널려 있다. 이건 도메인 모델 패턴이라고 할 수 없다.

🟡 풍성한 모델의 DB 매핑 어려움은 **ORM**이 푼다. 그래서 JPA를 쓰면 풍성한 도메인 모델을 쓰기가 훨씬 수월해진다 → [[도메인 모델과 JPA 엔티티를 분리해야 하는가]]

### 구성 요소

| | 예 |
|---|---|
| 엔티티 | `Member` — 속성과 행위를 함께 |
| 값 객체 | `Email`, `Profile` — 조건을 가진 값 |
| 열거형 | `MemberStatus` |
| **도메인 서비스** | `PasswordEncoder` — 🟢 인코딩 **구현**은 도메인의 관심사가 아니라 보안이라는 기술 관심사다. 도메인엔 인터페이스만 두고 필요한 시점에 메서드 레벨로 주입받는다 (전략 패턴) |

## 코드에 닿는 지점

전체를 뒤집을 수 없어도 내일 당장 할 수 있는 넷.

> 🟡 ① JPA 엔티티에 **속성만 담지 말고** 관련 도메인 로직·행위를 같이 넣는다. ② 외부에서는 **그 메서드를 통해서만** 쓰게 제한한다. ③ 상태를 꺼내서 비교하지 말고 `isActive()`로 물어본다. ④ **세터를 쓰지 않는다** — 로직 처리 코드 안에서 자연스럽게 속성이 바뀌고 필요한 상태가 검증되게 한다.

## 트레이드오프

| 쓸 때 | 트랜잭션 스크립트를 쓸 때 |
|---|---|
| 규칙이 있고 오래 유지할 도메인 | 규칙 없는 CRUD, 일회성 배치 |
| ORM 도움을 받을 수 있을 때 | 매핑이 감당 안 되는 레거시 스키마 |

**패턴 자체가 못 하는 것**: 작업 단위 API가 모델 안에 정의돼 있지 않다. 그래서 [[애플리케이션 서비스]]가 반드시 따라붙는다.
