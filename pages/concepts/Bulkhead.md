## 한 줄 정의

> 🟡 **한 종류의 작업이 자원을 다 써 버려도 다른 작업은 계속 돌아가도록 자원 풀을 미리 갈라 두는 것.** 배의 격벽에서 온 이름 — 한 구획에 물이 차도 배 전체는 가라앉지 않는다.

## 왜 필요한가

장애는 대개 **직접 고장난 곳이 아니라 자원을 공유하던 곳에서 터진다.**

PSP가 느려져 응답이 20초씩 걸린다고 하자. 스레드·HTTP 커넥션·DB 커넥션을 모두 공유하고 있으면, 결제 요청이 커넥션 풀을 전부 붙잡고 대기한다. 그 순간 **결제와 아무 상관없는 조회 API도 커넥션을 못 얻어 같이 죽는다.** 하나의 느림이 전면 장애가 되는 경로다.

[[복구 워커]]도 같은 위험을 만든다. 장애 복구 직후 밀린 대상 수천 건이 한꺼번에 PSP를 호출하면, 정상 결제가 자원을 못 얻는다.

## 어떻게 동작하는가

> 🔴 **Bulkhead는 스레드 풀만 뜻하지 않는다.** 실제로 갈라야 하는 것은 다섯 가지다.

| 자원 | 가르는 방법 |
|---|---|
| 스레드 / 이벤트 루프 | 작업별 별도 `Scheduler` 또는 Executor |
| **HTTP 커넥션 풀** | PSP별·용도별로 `WebClient` 인스턴스를 분리 |
| **DB 커넥션 풀** | 온라인 경로와 배치·복구 경로에 별도 DataSource |
| 동시 실행 수 | Semaphore, `flatMap(fn, concurrency)` |
| 유입량 | Rate Limit, 큐 크기 상한 |

여기에 [[재시도와 백오프]]와의 상호작용이 하나 있다. 🟢 재시도는 **부하를 증폭시킨다** — PSP가 느려서 재시도가 늘면 그만큼 커넥션 점유도 늘어난다. Bulkhead 없이 재시도만 켜면 장애가 빨라진다.

## 코드에 닿는 지점

```java
// 복구 경로는 동시 실행 수를 명시적으로 제한한다.
// 무제한 flatMap 은 PSP QPS 와 커넥션 풀을 그대로 초과한다
Flux.fromIterable(pendingPayments)
    .flatMap(this::recover, /* concurrency */ 8)
    .subscribe();
```

WebFlux에서는 `flatMap`의 concurrency 기본값(256)이 사실상 무제한처럼 동작한다. PSP Rate Limit과 `max.poll.interval.ms`를 넘지 않는 값으로 반드시 지정한다.

## 트레이드오프

| 쓸 때 | 안 쓸 때 |
|---|---|
| 응답 시간이 크게 다른 작업이 자원을 공유할 때 | 작업 종류가 하나뿐일 때 |
| 하나가 죽어도 나머지는 살아야 할 때 (결제 vs 조회) | 어차피 하나 죽으면 전체가 무의미할 때 |

대가는 **자원의 총 활용률 저하**다. 풀을 넷으로 가르면 한 풀이 놀아도 다른 풀이 빌려 쓰지 못한다. 그리고 풀마다 크기를 정해야 하는데, 그 값은 측정 없이는 정할 수 없다.
