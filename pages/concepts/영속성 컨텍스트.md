## 한 줄 정의

엔티티를 **관리 중인 상태로 붙들어 두는 공간**. 같은 트랜잭션 안에서 같은 식별자의 엔티티가 하나임을 보장하고, 변경을 모아 뒀다가 DB에 반영한다.

## 왜 필요한가

엔티티가 지금 어떤 상태인지 모르면 `save()` 한 줄이 INSERT가 될지 UPDATE가 될지 예측할 수 없다.

```text
NEW(Transient)
    ↓ persist()
MANAGED
    ↓ 컨텍스트 종료 / clear()
DETACHED
    ↓ merge()
MANAGED 인스턴스를 새로 반환
```

🟡 **상태는 객체 자체의 속성이 아니라 "지금 이 컨텍스트가 이 객체를 붙들고 있는가"다.** 같은 객체가 컨텍스트에 따라 MANAGED이기도 하고 DETACHED이기도 하다.

## 어떻게 동작하는가

### `save()`는 두 갈래로 갈린다

Spring Data JPA의 `save()`는 엔티티가 신규인지 판단해 `persist()` 또는 `merge()`를 호출한다. 판단 기준은 보통 **식별자가 비어 있는가**다.

🔴 **그래서 ID를 손으로 채운 신규 엔티티가 사고를 낸다.** 테스트 Fixture에서 이런 일이 실제로 일어난다.

```text
Course       id = null      → 신규로 판단 → persist 방향
CourseDetail id = 임의의 값  → 이미 있던 엔티티처럼 보임
```

`Course`가 persist되면서 cascade로 `CourseDetail`도 persist하려는데, 그쪽엔 ID가 이미 있으니 신규로 보이지 않는다.

```text
detached entity passed to persist
```

DB에 저장됐다가 떨어져 나온 게 아니라 **처음부터 그렇게 보이도록 만들어진 것**이다. 해결은 Fixture에서 DB 생성 ID를 직접 채우지 않는 것이다 → [[테스트 픽스처 상속 구조]]

### `merge()`는 원본을 바꾸지 않는다

```java
Course managed = entityManager.merge(detached);
```

🔴 **`detached` 객체가 managed로 변하는 게 아니다.** 상태를 복사한 **새로운 인스턴스**가 반환된다. 원본을 계속 쓰면 변경이 반영되지 않는다.

그래서 `save()` 결과는 반환값을 받아 쓰는 습관이 안전하다.

```java
course = courseRepository.save(course);
```

### `flush()`와 `clear()`는 다른 일을 한다

| | 하는 일 | 하지 않는 일 |
|---|---|---|
| `flush()` | 변경 내용을 DB SQL로 반영 | 트랜잭션을 끝내지 않는다 |
| `clear()` | 컨텍스트를 비운다. 관리하던 엔티티가 DETACHED가 된다 | DB를 건드리지 않는다 |

## 코드에 닿는 지점

Repository 테스트에서 둘을 붙여 쓰는 이유가 여기 있다.

```java
repository.save(course);
entityManager.flush();
entityManager.clear();

repository.findById(course.getId());   // 1차 캐시가 아니라 DB에서 다시 읽는다
```

`clear()` 없이 `findById()`를 하면 1차 캐시의 그 객체가 그대로 나와서, **매핑이 실제로 DB에 잘 적히는지 검증하지 못한다.** [[낙관적 락과 Hibernate SQL 관찰]]이 SQL을 직접 보는 것도 같은 이유다.

## 트레이드오프

- **1차 캐시는 공짜가 아니다.** 같은 트랜잭션이 길어지면 관리 대상이 쌓이고, `flush()` 때마다 전체 변경 감지 비용이 든다
- 🔴 **`merge()`로 detached를 되살리는 건 최후 수단에 가깝다.** 어떤 필드가 덮이는지 추적하기 어렵고, 부분 수정 의도가 전체 덮어쓰기로 바뀔 수 있다. 가능하면 짧은 트랜잭션 안에서 조회 → 변경으로 끝낸다
- 컨텍스트 경계를 넘겨 엔티티를 들고 다니면 [[Optimistic Offline Lock]]의 문제 영역으로 넘어간다

## 아직 안 적은 것

🔴 이 페이지는 **상태 전이와 `merge`/`flush`/`clear`까지만** 다룬다. 같이 묶여 있어야 할 [[더티 체킹]] · [[JPA N+1]] · 쓰기 지연은 아직 없다.
