## 한 줄 정의

> 🟡 **존재하지 않는 행의 자리(gap)에 거는 락.** 팬텀 리드를 막기 위한 장치이고, 대가는 "아무것도 없는 구간"을 두고 벌어지는 락 경합과 데드락이다.

- **갭 락(Gap Lock)** — 인덱스 레코드 **사이의 빈 구간**을 잠근다. 그 구간에 새 행을 INSERT하지 못하게 한다
- **넥스트키 락(Next-Key Lock)** — 레코드 락 + 그 앞의 갭 락. InnoDB의 `REPEATABLE READ` 기본 동작

## 왜 필요한가

`REPEATABLE READ`에서 같은 조건으로 두 번 조회했을 때 없던 행이 생기면 **팬텀**이다. 이미 존재하는 행만 잠가서는 막을 수 없다 — 아직 없는 행은 잠글 대상이 없기 때문이다. 그래서 InnoDB는 **행이 들어올 자리**를 잠근다.

## 어떻게 동작하는가

```
인덱스:  … 10 … 20 … 30 …

SELECT * FROM t WHERE id BETWEEN 15 AND 25 FOR UPDATE;

  잠기는 것: 20(레코드) + (10,20) 갭 + (20,30) 갭
  ⇒ 여기에 id=17 이나 id=23 을 INSERT 하려는 트랜잭션은 대기한다
```

> 🔴 **서로 다른 값을 넣는 INSERT끼리도 부딪힌다.** 두 트랜잭션이 각각 `id=17`, `id=23`을 넣으려 해도 둘 다 같은 갭에 걸려 있으면 순서에 따라 데드락이 된다. "키가 다르니 안 부딪히겠지"라는 직관이 여기서 깨진다.

UNIQUE 인덱스 INSERT도 같은 경로를 탄다. 중복 검사를 위해 삽입 지점 주변을 잠그기 때문에, `idempotency_key`처럼 **랜덤에 가까운 값을 동시에 대량 INSERT**하면 인접 구간이 겹치며 경합이 생긴다([[외래키 제약과 락 경합]]).

🟢 갭 락은 **인덱스가 있어야 좁게 걸린다.** 조건 컬럼에 인덱스가 없으면 InnoDB는 전체 스캔을 하며 지나간 모든 행과 갭을 잠근다 — 사실상 테이블 락이다. 락 범위 문제의 상당수는 인덱스 문제다.

## 코드에 닿는 지점

```sql
-- 격리수준을 낮춰 갭 락을 없애는 방법 (팬텀을 감수한다)
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 또는 유니크 인덱스로 정확히 한 행만 지목한다 (갭 없이 레코드 락만)
SELECT * FROM t WHERE id = 20 FOR UPDATE;
```

`READ COMMITTED`에서는 갭 락이 대부분 사라진다. MySQL 복제가 ROW 기반이면 이 격리수준으로 내리는 선택이 실무에서 흔하다.

## 트레이드오프

| 갭 락을 유지할 때 | 낮출 때 |
|---|---|
| 팬텀이 정합성을 깨는 조회-후-삽입 로직이 있을 때 | 동시 INSERT 처리량이 중요할 때 |
| 범위 조건으로 예약·선점하는 패턴 | 조건이 항상 유니크 키 하나일 때 (갭 락이 애초에 안 걸린다) |
