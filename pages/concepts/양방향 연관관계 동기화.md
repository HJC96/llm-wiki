## 한 줄 정의

한 관계를 양쪽 객체가 각자 들고 있을 때, **둘을 항상 같이 바꿔 주는 일**. 한쪽만 고치면 객체 그래프와 DB가 서로 다른 말을 한다.

## 왜 필요한가

`Section`은 `List<Lesson>`을 들고 있고 `Lesson`은 `section`을 들고 있다. 같은 사실을 두 군데 적어 둔 것이다.

```java
section.lessons.add(lesson);   // 한쪽만 바꾸면
// lesson.section 은 여전히 옛 Section
```

🔴 **이 상태에서 조회 결과는 "어느 쪽을 봤느냐"에 따라 달라진다.** 컬렉션으로 보면 옮겨진 것 같고, 자식에서 부모를 보면 안 옮겨졌다. 게다가 외래키를 실제로 쥔 쪽은 보통 자식(`lesson.section`)이라, **컬렉션만 고치면 DB에는 아무 일도 일어나지 않는다.**

그래서 둘을 한 자리에서 같이 바꾸는 메서드를 둔다.

```java
void addLesson(int insertIndex, Lesson lesson) {
    lesson.moveTo(this);              // 자식 → 부모
    this.lessons.add(insertIndex, lesson);  // 부모 → 자식
}
```

🟡 **이 메서드의 존재 이유는 편의가 아니라 불변식이다.** "두 방향이 항상 일치한다"를 호출자가 아니라 객체가 스스로 보장한다. [[애그리거트 경계 정하기]]에서 루트만 public으로 열어 두는 것과 같은 이유다.

## 어떻게 동작하는가

메서드를 부른 객체가 `this`다. 그래서 같은 `this`라도 어느 메서드 안이냐에 따라 가리키는 게 달라진다.

```java
void moveAllLessonsTo(Section target, int insertIndex) {
    while (!this.lessons.isEmpty()) {
        target.addLesson(insertIndex++, this.lessons.getFirst());
        this.lessons.removeFirst();
    }
}
```

```text
moveAllLessonsTo 안에서   this = 내보내는 쪽(source),  target = 받는 쪽
addLesson 안에서          this = target  ← target.addLesson(...)으로 불렀으므로
```

`s2.moveAllLessonsTo(s1, 2)`라면 s2의 Lesson이 s1으로 간다.

이동은 **더하기와 빼기가 한 쌍**이다.

```java
target.addLesson(...);        // 받는 쪽에 넣고
this.lessons.removeFirst();   // 내보내는 쪽에서 빼야
```

🔴 **빼기를 빠뜨리면 `OutOfMemoryError`까지 간다.** `removeFirst()`를 누락해 `this.lessons`가 비워지지 않았고, `while`이 끝나지 않으면서 대상 컬렉션이 계속 커져 메모리가 터졌다. 단순히 안 끝나는 게 아니라 **프로세스가 죽는다.** 이동을 "추가"로만 생각하면 반드시 물리는 함정이다.

**삭제 후 index는 즉시 바뀐다.** `[S0, S1]`에서 S0을 지우면 기존 S1이 곧바로 index 0이 된다. 그래서 Section을 지울 때 Lesson을 어디로 보낼지가 경우마다 다르다.

| 지우는 Section | Lesson 목적지 | 시작 index |
|---|---|---|
| 첫 번째 | 다음 Section 앞쪽 | `0`부터 증가 |
| 그 외 | 이전 Section 뒤쪽 | 이전 Section의 `lessons.size()` |
| 마지막 하나 | 🔴 삭제 불가 | — |

마지막 Section을 막는 건 도메인 규칙이다. `IndexOutOfBoundsException`이 나게 두지 않고 **의미 있는 `IllegalStateException`으로 규칙을 코드에 드러낸다.**

**`insertIndex++`도 같은 이유다.** 여러 개를 옮기면서 매번 같은 자리에 넣으면 순서가 뒤집힌다.

```text
[L0, L1]을 앞쪽으로 이동
index 0 고정 →  [L1, L0]   ← 뒤집힘
insertIndex++ → [L0, L1]   ← 유지
```

이건 [[컬렉션 순서와 @OrderColumn]]이 관리하는 그 순서를 **도메인 코드가 먼저 올바르게 만들어 줘야 한다**는 뜻이다.

## 코드에 닿는 지점

책임이 셋으로 갈린다.

```text
Curriculum   Section 간 이동을 결정한다 (어디로 보낼지)
Section      Lesson 목록을 관리한다
Lesson       자신이 속한 Section을 바꾼다
```

이 도메인의 Section 삭제 규칙도 Curriculum이 정한다.

| 상황 | 처리 |
|---|---|
| 첫 Section 삭제 | Lesson을 **다음** Section 앞쪽으로 |
| 그 외 Section 삭제 | Lesson을 **이전** Section 뒤쪽으로 |
| Section이 하나뿐 | 삭제 불가 |

**테스트는 스냅샷 record로 비교한다.** 엔티티 그래프를 그대로 비교하면 양방향 참조 때문에 읽기 어렵다. `SectionContent` / `LessonContent` 같은 단순 record로 한 번 변환해 구조와 순서만 본다 → [[테스트 픽스처 상속 구조]]

## 트레이드오프

- 🔴 **양방향을 유지하는 비용이 계속 든다.** 관계를 바꾸는 경로가 늘 때마다 동기화를 빠뜨릴 지점이 생긴다. **단방향으로 충분한지 먼저 묻는 게 낫다** — 컬렉션을 순회할 일이 없으면 자식이 부모만 들고 있으면 된다
- **`@ToString`에 연관을 넣으면 순환 참조가 난다.** 양방향이라 서로를 부른다. `exclude`로 빼는 게 관행
- 🔴 **동기화 메서드가 있어도 필드를 직접 건드리면 소용없다.** 세터를 열어 두면 불변식이 우회된다. 컬렉션은 불변 뷰로 내보내고 변경은 메서드로만 받는 쪽이 안전하다
- 객체 그래프를 맞춰 놓아도 DB 반영 시점은 [[영속성 컨텍스트]]가 정한다. 둘을 같은 것으로 착각하면 "코드는 맞는데 DB가 다르다"가 된다
