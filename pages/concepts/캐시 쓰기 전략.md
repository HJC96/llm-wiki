## 한 줄 정의

🟡 쓰기를 캐시에 **언제 어떻게 반영하느냐** — Write Through / Write Around / Write Behind 셋은 이 한 질문의 세 답이라 나란히 봐야 한다.

## 왜 필요한가

읽기 패턴([[Cache Aside]]·[[Read Through]])만 정하면 절반이다. 쓰기가 일어났을 때 캐시를 **채울지, 비울지, 나중에 저장소로 흘릴지**를 정해야 캐시 정책이 완성된다.

## 어떻게 동작하는가

| 전략 | 흐름 | 쓰기 직후 캐시 | 저장소 반영 |
|---|---|---|---|
| **Write Through** | `store.save` → `cache.put` | 최신 값 있음 | 요청 안에서 즉시 |
| **Write Around** | `store.save` → `cache.evict` | **해당 key 없음** | 요청 안에서 즉시 |
| **Write Behind** | `cache.put` → pending 추가 → `flush` | 최신 값 있음 | **나중에** |

🟢 Write Behind의 정체는 관찰 한 줄로 드러난다 — **쓰기 직후 저장소는 이전 값, 캐시는 최신 값.**

🔴 Write Around에서 **`evict`가 아니라 아무것도 안 하면** 기존 캐시 값이 저장소보다 오래된 채로 남는다. "캐시를 채우지 않는다"와 "캐시를 건드리지 않는다"는 다르다.

## 코드에 닿는 지점

```java
@CachePut(cacheNames = "book", key = "#book.id")   // Write Through
public Book save(Book book) { return repository.save(book); }

@CacheEvict(cacheNames = "book", key = "#book.id") // Write Around
public Book save(Book book) { return repository.save(book); }
```

Write Behind는 Spring 애너테이션으로 표현되지 않는다 — 직접 큐와 플러시를 만든다.

## 트레이드오프

| 상황 | 고를 것 |
|---|---|
| 일반적인 조회 캐시 | **[[Cache Aside]] + Write Around** (기본값) |
| 쓰기 직후 바로 읽는 요청이 많음 | + Write Through |
| 쓰기는 많고 실제 조회는 적음 | + Write Around (읽히지 않을 데이터의 캐시 유입 방지) |
| 쓰기 처리량이 매우 중요 | + Write Behind **+ 영속 큐** |

🔴 **Write Behind는 메모리 큐만 쓰면 유실된다.** 플러시 전에 프로세스가 죽으면 저장소에 없는 쓰기가 사라진다. 영속 큐가 함께 있어야 한다 — [[커밋 후 이벤트 발행]]과 같은 성질의 문제다.

🔴 **Write Through는 쓰기 지연을 늘린다.** 저장소 쓰기 + 캐시 쓰기가 요청 안에 다 들어간다. 읽히지 않을 데이터까지 캐시에 넣는 비용도 있다.

💬 Cache Aside 코드와 Write Around 코드는 거의 같다. 이름이 다른 이유는 **관찰 대상**이 달라서다 — 앞은 읽기 miss를 누가 처리하는지, 뒤는 쓰기 때 캐시를 채우는지.
