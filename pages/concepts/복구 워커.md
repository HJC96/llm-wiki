## 한 줄 정의

> 🟡 **온라인 요청 경로에서 끝나지 못한 작업을 나중에 비동기로 끝내 주는 주기 작업.** 사용자의 요청은 이미 끊겼지만 시스템의 상태는 아직 중간에 있다.

## 왜 필요한가

프로세스는 어느 줄에서든 죽는다. 죽은 자리가 `EXECUTING`이면 그 결제는 아무도 건드리지 않는 채로 영원히 남는다. 사용자는 결제창을 닫았고, 재시도할 스레드도 없다.

> 🟡 온라인 경로의 재시도([[재시도와 백오프]])와 복구 워커는 **다루는 시간 규모가 다르다.** 재시도는 초 단위로 같은 요청 안에서, 복구는 분·시간 단위로 요청 밖에서. 앞의 것만 있으면 "요청이 끊긴 뒤의 실패"를 아무도 줍지 않는다.

## 어떻게 동작하는가

1. **후보 조회** — `status IN (EXECUTING, UNKNOWN)` **그리고** `updated_at < stale threshold` **그리고** `next_retry_at <= now`
2. **처리권 점유** — Lease 또는 CAS. 인스턴스가 여러 대이므로 반드시 필요하다
3. **먼저 조회, 그다음 실행** — 새 결제를 만들기 전에 **PSP 결제 조회 API로 기존 결과를 확인**한다
4. 재승인이 필요하면 **원래 Idempotency Key** 그대로
5. `attempts`, `last_error`, `next_retry_at` 갱신. 한도를 넘으면 운영자 확인 대상으로

> 🔴 상태만 조건으로 걸면 **지금 정상 처리 중인 건까지 집어간다.** `EXECUTING`은 방금 시작한 결제도 갖는 상태다. `updated_at`으로 "충분히 오래 머물렀다"를 함께 걸어야 정상 경로와 복구 경로가 충돌하지 않는다.

**인스턴스 분할보다 중요한 것** — StatefulSet ordinal의 modulo로 대상을 나누는 방식은 Replica 수가 바뀌는 순간 대상이 재배치된다. 그 순간 두 인스턴스가 같은 건을 집는다. 🟢 분할은 성능 최적화일 뿐이고, **정확성은 작업 자체의 멱등성과 Lease가 책임진다.**

## 코드에 닿는 지점

```sql
-- 후보를 집으면서 동시에 점유한다. 조회와 점유가 나뉘면 그 사이에 경쟁이 생긴다
SELECT * FROM payment_orders
 WHERE status IN ('EXECUTING','UNKNOWN')
   AND updated_at < NOW() - INTERVAL 5 MINUTE
   AND next_retry_at <= NOW()
 LIMIT 100
 FOR UPDATE SKIP LOCKED;
```

`SKIP LOCKED`는 다른 워커가 잡은 행을 기다리지 않고 건너뛴다. 여러 인스턴스가 같은 쿼리를 동시에 돌려도 서로 다른 행을 가져간다.

## 트레이드오프

| 둘 때 | 안 둘 때 |
|---|---|
| 중간 상태가 **외부 부수효과**를 동반할 때 (결제, 발송, 재고) | 실패하면 그냥 사용자가 다시 하면 되는 작업 |
| 결과 조회 API가 있어서 수렴이 가능할 때 | 조회할 수단이 없어 결국 수동 처리로 갈 때 — 그래도 목록은 필요하다 |

대가는 **자원 경합**이다. 복구 트래픽이 정상 결제와 같은 DB 커넥션 풀·HTTP 커넥션 풀을 쓰면, 장애 직후 밀린 복구 대상이 한꺼번에 몰려 정상 결제를 마비시킨다. 그래서 [[Bulkhead]]가 짝으로 따라온다.
