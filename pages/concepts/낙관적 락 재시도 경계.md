## 한 줄 정의

> 🟡 **재시도 경계는 트랜잭션 경계보다 반드시 바깥이어야 한다.** 충돌을 감지한 트랜잭션은 이미 죽은 트랜잭션이라 그 안에서 다시 시도할 수 없다.

`@Version`을 붙이는 것은 [[낙관적 락]]의 절반이고, 나머지 절반이 이 경계 설계다.

## 왜 필요한가

가장 먼저 떠오르는 코드가 정확히 틀린 코드다.

```java
@Transactional
public void save() {
    try {
        saveWallet();
    } catch (ObjectOptimisticLockingFailureException e) {
        // retry  ← 여기서 재시도해도 소용없다
    }
}
```

> 🔴 트랜잭션 안에서 Optimistic Lock 예외가 나면 그 트랜잭션은 **rollback-only로 마킹된다.** `catch`로 예외를 잡아도 트랜잭션 자체는 되살아나지 않고, 커밋 시점에 `UnexpectedRollbackException`으로 터진다. 예외를 삼켜서 조용히 롤백되는 경우가 더 나쁘다 — 로그에는 성공처럼 보인다.

## 어떻게 동작하는가

```
save()                                    ← 트랜잭션 아님
 │
 ├─ Tx#1 { wallet 저장; transaction 저장 }
 │      실패 (version 충돌)
 │
 ├─ delay + jitter
 ├─ 최신 wallet 재조회          ← 트랜잭션 밖
 ├─ 정산 금액 다시 적용          ← 트랜잭션 밖
 │
 └─ Tx#2 { wallet 저장; transaction 저장 }
```

재시도 설계에서 지켜야 하는 다섯 가지.

1. **실패한 트랜잭션을 재사용하지 않는다** — 매 시도가 새 트랜잭션
2. **최신 값을 다시 읽고 연산을 다시 적용한다** — 이전에 계산한 `newBalance`를 그대로 쓰면 [[Lost Update]]가 그대로 재현된다
3. **bounded retry** — 최대 3회 정도. 무한 재시도는 장애를 키운다
4. **delay + jitter** — 동시에 실패한 트랜잭션들이 동시에 재시도하면 다시 충돌한다
5. **트랜잭션은 짧게** — 재조회·계산·지연은 전부 트랜잭션 밖. 실제 DB 변경 구간만 묶는다

> 🟢 jitter가 하는 일은 재시도 시점을 흩뜨리는 것이다. `50ms / 82ms / 117ms`처럼 서로 다른 시각에 다시 시도해야 두 번째 충돌 확률이 떨어진다. 고정 지연은 충돌한 트랜잭션들을 계속 같은 박자로 만나게 한다.

## 코드에 닿는 지점

```java
public void save(...) {
    for (int attempt = 0; attempt < MAX_RETRY; attempt++) {
        try {
            executeTransaction(...);
            return;
        } catch (ObjectOptimisticLockingFailureException e) {
            if (attempt == MAX_RETRY - 1) throw new RetryExhaustedException();
            sleep(baseDelay + jitter());
            wallet = walletRepository.findById(walletId).add(amount);  // 재조회 + 재계산
        }
    }
}

private void executeTransaction(...) {
    transactionTemplate.executeWithoutResult(status -> {
        walletRepository.save(wallet);
        walletTransactionRepository.save(transaction);
    });
}
```

> 🟡 `private` 메서드에 `@Transactional`을 붙여도 안 걸린다([[프록시 자기호출 문제]]). 그래서 `TransactionTemplate`을 쓴다. 별도 빈으로 분리해 `REQUIRES_NEW`를 거는 방법도 있지만, 트랜잭션 경계를 코드에서 눈으로 보게 하려면 `TransactionTemplate` 쪽이 명시적이다.

**동시성 테스트** — 여러 스레드로 같은 지갑을 동시에 갱신해 최종 잔액이 정확한지 본다. 타이밍에 따라 우연히 통과할 수 있으므로 `@RepeatedTest`로 여러 번 돌린다.

## 트레이드오프

| 재시도로 풀 때 | 다른 걸 고를 때 |
|---|---|
| 충돌이 드물 때 — 재시도 비용 < 락 대기 비용 | **Hot Key**일 때. 인기 판매자 지갑에 정산이 몰리면 재시도가 폭증한다 |
| 재계산이 싼 연산일 때 (`balance + amount`) | 재계산이 비싸거나 부수효과가 있을 때 |

Hot Key의 대안: [[원자적 UPDATE로 푸는 동시성]](`balance = balance + ?`), 키별 직렬 처리, 파티셔닝, 단일 Writer.
