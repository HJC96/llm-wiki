## 한 줄 정의

> 🟡 **도메인 모델 앞에 놓인, 작업 단위 API를 제공하는 얇은 계층.** 도메인 로직을 여기 넣지 않기 때문에 코드가 아주 간결하다. **도메인 파사드(Facade)** 라고도 부른다.

여기서 API는 웹 API가 아니라 원래 뜻 — Application Programming Interface, **모듈이 외부에 공개한 인터페이스의 총칭**이다.

## 왜 필요한가

> 🔴 [[도메인 모델 패턴]]은 도메인의 정수를 잘 담지만 **작업 단위가 그 안에 정의돼 있지 않다.** 애플리케이션은 결국 "회원 가입을 완료시킨다" 같은 태스크 단위로 요청을 받아 처리해야 한다. 게다가 어떤 작업은 **하나 이상의 도메인 객체**를 쓰고, 도메인 로직 외에 **외부 시스템**과도 일해야 한다.

> 🔴 이 층이 없으면 컨트롤러(웹 기술 처리 계층)에서 도메인 객체를 직접 가져와 호출하고 변경하는 코드가 생긴다. **도메인에 대한 정보가 외부로 전부 유출된다.**

## 어떻게 동작하는가

3계층에 도메인 모델 패턴을 쓰면 도메인 계층 하나로는 작업 단위 API를 노출할 수 없다. 그래서 도메인을 **애플리케이션 서비스 / 도메인**으로 쪼갠다 — 개념적으로는 여전히 3계층, 실제로는 4계층.

```
Presentation
  ↓
Application Service   ← 작업 단위 절차형 API. 외부 시스템·DB 액세스도 여기서
  ↓
Domain                ← 순수하게 남긴다
  ↓
Infrastructure
```

> 🟡 도메인 계층이 인프라를 직접 쓰면 기술 코드가 다시 도메인 안으로 들어온다. **도메인은 순수하게 남기고, 외부 시스템 연결·DB 액세스는 애플리케이션 서비스가 직접 쓰게** 하는 편이 낫다. 이것이 [[계층형 아키텍처]]의 "완화된" 형태이고, 오늘날 가장 전형적인 구조다.

에릭 에반스의 『Domain-Driven Design』(2003)이 제시한 것도 정확히 이 **4계층**이다.

## 코드에 닿는 지점

```java
@Service
@RequiredArgsConstructor
public class MemberRegisterService implements MemberRegister {   // Provided Interface
    private final MemberRepository memberRepository;             // Required Interface
    private final PasswordEncoder passwordEncoder;

    @Transactional
    public Member register(MemberRegisterRequest request) {
        checkDuplicate(request.email());
        Member member = Member.register(request, passwordEncoder);  // 도메인이 규칙을 안다
        return memberRepository.save(member);
    }
}
```

요청 값 **밸리데이션**은 여기서 한다. 도메인 불변식(값 객체의 형식 검증 등)은 도메인 안에서.

## 트레이드오프

| 둘 때 | 안 둘 때 |
|---|---|
| 도메인 모델 패턴을 쓸 때는 **사실상 필수** | 트랜잭션 스크립트 방식이면 서비스가 이미 그 역할을 한다 |
| 유스케이스가 여러 도메인 객체를 조율할 때 | 단일 엔티티 CRUD뿐일 때 |

🔴 대가는 **비대해지기 쉽다는 것**이다. "얇은 층"이라는 규칙을 안 지키면 도메인 로직이 여기로 새고, 그러면 도메인은 다시 애니믹이 된다.
