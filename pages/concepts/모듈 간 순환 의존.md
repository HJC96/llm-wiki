## 한 줄 정의

두 모듈이 서로를 참조하는 상태. **기능이 필요한 방향과 코드가 의존하는 방향을 같게 두면** 생긴다. DIP로 인터페이스 소유권을 옮겨 끊는다.

## 왜 필요한가

의존한다는 건 **의존 대상의 변경이 나에게 영향을 줄 수 있다**는 뜻이다. `A → B`면 B가 바뀔 때 A가 흔들린다. `A ↔ B`가 되면 서로 흔든다.

```text
독립적으로 변경하기 어렵다
따로 테스트하기 어렵다
모듈 경계가 흐려진다
한쪽 변경이 계속 전파된다
```

🟡 **Aggregate 내부에서는 양방향 참조를 써도 된다**([[양방향 연관관계 동기화]]). 문제는 **Aggregate/Component 경계를 넘어설 때**다. 경계를 넘는 의존은 단방향으로 유지한다.

## 어떻게 동작하는가

### 순환이 생기는 순간

Course와 Curriculum은 다른 Aggregate이고, 원래 의존은 한 방향이었다.

```text
Curriculum Module ──→ Course Module
```

여기에 "Course를 만들면 빈 Curriculum도 같이 만들자"가 들어온다. 가장 단순한 구현은 `CourseApplicationService`가 `CurriculumCoordinator`를 직접 부르는 것이다. 기능은 잘 돈다.

```text
Curriculum ──→ Course ──→ Curriculum      ← 순환
```

🟢 이 도메인에서는 `Free of Cycles` 아키텍처 테스트가 이걸 잡아냈다. 사람이 리뷰로 지키던 걸 CI가 지키게 한 사례다 → [[ArchUnit으로 아키텍처 강제하기]]

### DIP로 끊는다 — 핵심은 인터페이스 **소유권**

🔴 **"구현체 대신 인터페이스에 의존했다"만으로는 아무것도 역전되지 않는다.**

```text
application/     OrderService
infrastructure/  OrderRepository(interface) · JpaOrderRepository
```

Application이 인터페이스를 쓰고는 있지만 그 인터페이스가 Infrastructure에 있다. 코드 의존성은 여전히 `Application → Infrastructure`다. **인터페이스를 하나 끼웠을 뿐 방향은 그대로다.**

인터페이스를 **필요로 하는 쪽**으로 옮겨야 역전된다.

```text
Course Module
    CourseModifyService
           ↓
    CurriculumCreator (interface)   ← 소유권이 여기 있다
           ▲
           │ implements
Curriculum Module
    CurriculumCoordinator
```

```java
// Course Module에 둔다
interface CurriculumCreator {
    Long createCurriculum(Course course);
}
```

🟡 **실행 흐름과 코드 의존 방향이 반대가 된다.**

| | 방향 |
|---|---|
| 실행 흐름 | Course → Curriculum 생성 |
| 코드 의존성 | Curriculum → Course |

기능은 원하는 대로 흐르면서 원래의 단방향이 유지된다.

## 코드에 닿는 지점

**계약은 클라이언트 관점으로 좁게 만든다.** Course가 알고 싶은 건 Curriculum 모듈 전체가 아니라 "하나 만들어 줘" 하나다. 그래서 `CurriculumCoordinator`를 그대로 노출하지 않고 `CurriculumCreator`만 정의한다.

🔴 **반환 타입으로 의존이 되살아난다.** `Curriculum` 객체를 돌려주면 Course가 그걸 받아 조작하기 시작하고, 그 순간 Course 코드가 Curriculum 도메인 타입에 다시 의존한다. 순환이 조용히 복구된다.

```java
Long createCurriculum(Course course);   // 필요한 만큼만
```

**인터페이스 위치뿐 아니라 시그니처에 등장하는 타입까지 봐야 한다.** 이게 놓치기 쉬운 지점이다.

## 트레이드오프

- 🔴 **DIP와 DI는 다르다.** DI는 의존성을 외부에서 주입하는 *방법*이고, DIP는 의존 방향을 어떻게 설계할지에 대한 *원칙*이다. 스프링을 쓴다고 DIP가 지켜지지 않는다
- **역전은 공짜가 아니다.** 인터페이스가 하나 늘고, 구현이 어느 모듈에 있는지 추적이 한 단계 길어진다. 모듈이 둘뿐이고 앞으로도 그렇다면 과할 수 있다
- 🔴 **다른 해법도 있다.** 도메인 이벤트로 `CourseCreated`를 발행하고 Curriculum이 구독하면 Course는 Curriculum을 아예 모른다. 결합은 더 낮아지지만 동기 보장이 사라진다. 이 소스는 그 선택지를 비교하지 않는다
- 순환은 **기능 요구가 늘 때 생긴다.** 초기 설계가 옳았어도 요구가 추가되면 다시 검사해야 하므로, 사람 눈이 아니라 테스트로 잡는 게 맞다
