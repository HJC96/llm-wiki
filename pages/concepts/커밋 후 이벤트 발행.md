## 한 줄 정의

🟡 상태 변경과 이벤트 발행이 원자적일 수 없다면, 둘 중 **되돌릴 수 있는 쪽(DB)을 먼저 확정하고 되돌릴 수 없는 쪽(발행)을 나중에** 둔다.

## 왜 필요한가

이벤트 발행을 트랜잭션 안에 넣으면, 이벤트를 보낸 뒤 DB 업데이트가 실패하는 순간 **DB에는 없는 사실을 남에게 알린 상태**가 된다.

🟢 구체적으로: Product는 주문이 요청됐다고 믿고 재고를 깎는데, Order의 DB에는 그 주문이 `CREATED` 그대로다. 아무도 되돌릴 수 없다 — 발행은 취소가 안 되기 때문이다.

## 어떻게 동작하는가

커밋이 확정된 뒤에만 발행하도록 콜백을 건다.

```java
@Transactional
public void placeOrder(PlaceOrderCommand command) {
    Order order = orderRepository.findById(command.orderId()).orElseThrow();
    order.request();                                    // CREATED → REQUESTED
    orderRepository.save(order);

    OrderPlacedEvent event = toEvent(order, ...);

    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {
            @Override
            public void afterCommit() {                 // ← 커밋이 끝난 뒤에만 발행
                orderPlacedProducer.send(event);
            }
        });
}
```

🟢 더 간결하게는 `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`로 같은 시점을 잡는다.

## 코드에 닿는 지점

| | 프레임워크가 해 주는 것 | 내가 정해야 하는 것 |
|---|---|---|
| `@TransactionalEventListener(AFTER_COMMIT)` | 콜백 시점 보장 | **유실 허용 여부** (Outbox 필요성) |

## 트레이드오프

🔴 **이 방식도 완벽하지 않다.** 커밋은 됐는데 **발행 직전에 프로세스가 죽으면 이벤트가 유실된다.** 커밋과 발행 사이에 창이 남는다.

완전히 막으려면 이벤트를 **같은 트랜잭션에서 DB 테이블에 저장하고** 별도 프로세스가 읽어서 발행하는 [[Outbox 패턴]]이 필요하다.

| 방식 | 유실 창 | 비용 |
|---|---|---|
| 트랜잭션 안에서 발행 | 없음, 대신 **없는 사실을 알림** | 낮음 |
| `AFTER_COMMIT` | 커밋~발행 사이 | 낮음 |
| [[Outbox 패턴]] | 없음 | 테이블 + 릴레이 프로세스 |

💬 대부분의 서비스는 `AFTER_COMMIT`으로 충분하다. Outbox는 **유실이 곧 사고인 영역**에서만 값을 한다. 이 판단을 안 하고 넘어가면 "왜 가끔 이벤트가 안 오지?"를 나중에 만난다.
