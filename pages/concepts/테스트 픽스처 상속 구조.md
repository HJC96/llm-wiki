## 한 줄 정의

테스트 공통 준비 코드를 추상 부모 클래스에 모으고, 자식 테스트가 상속해 쓰는 패턴. **반복은 줄지만 데이터의 출처가 흐려진다.**

## 왜 필요한가

Application Service 테스트마다 Member·Instructor를 만드는 코드가 반복된다. 이걸 부모로 올린다.

```java
abstract class BaseApplicationServiceTest {
    protected Member member;

    protected Member prepareMember() {
        Member newMember = createMember();
        this.member = newMember;
        return newMember;
    }
}
```

**`abstract`인 이유는 이 클래스 자체가 테스트 대상이 아니기 때문이다.** 직접 만들어 쓰는 게 아니라 상속해서 쓴다는 의도 표시다.

🔴 **`prepareMember()`는 추상 메서드가 아니다.** 클래스만 `abstract`이고 메서드는 구현돼 있다. 진짜 추상 메서드라면 `protected abstract Member prepareMember();`처럼 몸통이 없다. 둘을 헷갈리기 쉽다.

## 어떻게 동작하는가

### 상속은 객체를 둘로 만들지 않는다

부모 객체 하나 + 자식 객체 하나가 따로 생기는 게 아니다. **객체 하나 안에 상속받은 필드와 메서드가 함께 있다.**

```text
CourseServiceTest 객체 하나
├─ 부모에서 옴:  Member member · prepareMember()
└─ 자식에서 정의: testCreateCourse()
```

그래서 부모 메서드 안의 `this.member`에서 `this`는 실행 중인 **자식 객체**다.

`protected`는 자식에서 접근 가능하다는 뜻일 뿐, **값이 고정된다는 의미가 전혀 아니다.**

### `member` 필드는 "마지막에 만든 것"을 가리키는 슬롯이다

```java
Member member1 = prepareMember();   // this.member → A
Member member2 = prepareMember();   // this.member → B
```

🟡 **부모의 `member`는 가장 최근에 준비한 Member를 가리키는 편의용 슬롯이다.** 고정된 하나를 영원히 재사용하는 게 아니다.

이전 것이 사라지지도 않는다. `this.member`만 B로 바뀌고 `member1`은 여전히 A를 참조한다.

### 왜 캐싱하지 않는가

```java
if (member != null) return member;   // ← 이렇게 하면
```

`member1`과 `member2`가 같은 객체가 된다. 그런데 테스트는 **서로 다른 데이터**를 자주 필요로 한다(Member A + Instructor A / Member B + Instructor B). 그래서 `prepareMember()`는 캐시가 아니라 **"하나 새로 준비해 줘"라는 factory에 가깝다.**

## 코드에 닿는 지점

```java
prepareMember();                          // 한 명만 필요할 때
member.doSomething();

Member m1 = prepareMember();              // 여러 명 필요할 때
Member m2 = prepareMember();
```

🔴 **Fixture가 ID를 채우면 안 된다.** 신규 엔티티인데 DB 생성 ID를 손으로 넣으면 Hibernate가 기존 엔티티로 오인해 `detached entity passed to persist`가 난다 → [[영속성 컨텍스트]]

```java
new CourseDetail(null, ...);   // id는 null로
```

## 🔴 실제로 깨진 사례

`setUp()`에서 `this.instructor = A`를 저장해 뒀는데, 테스트 도중 `prepareInstructor()`를 다시 부르면서 **공통 필드가 조용히 B로 덮어써졌다.** 테스트는 여전히 A라고 믿고 진행해 잘못된 객체로 조회했다.

```java
setUp()                 this.instructor = A
...
prepareInstructor()     this.instructor = B   ← 여기서 바뀐 걸 아무도 모른다
assert(instructor ...)  A를 기대하지만 B다
```

🟡 **같은 타입 fixture가 둘 이상 필요한 순간 이 패턴은 위험해진다.** 반환값을 `instructor1` · `instructor2`로 받아 쓰면 애초에 생기지 않는다.

**`record` 테스트 클래스는 이 구조와 안 맞는다.** 테스트 클래스를 `record`로 선언하면 Bean 주입은 간결해지지만(record component로 받는다), **record component 외의 인스턴스 필드를 가질 수 없다.** `@BeforeEach`에서 만든 fixture를 필드에 저장하는 구조 자체가 불가능하다.

## 트레이드오프

| | 부모 필드를 쓰는 방식 | 반환값을 지역 변수로 받는 방식 |
|---|---|---|
| 테스트 본문 | 짧다 | 한 줄 늘어난다 |
| 데이터 출처 | 🔴 어디서 만들어졌고 언제 바뀌었는지 코드만 봐선 모른다 | 눈에 보인다 |
| 테스트 간 영향 | 🔴 상태가 부모에 얹혀 있다 | 격리된다 |

```java
Member member = prepareMember();                 // 더 명시적인 쪽
Instructor instructor = prepareInstructor(member);
```

🟡 **강의 방식이 Java·Spring의 권장 패턴이라서가 아니라, Fixture 반복을 줄이려는 편의 설계다.** 팀이 명시성을 더 치면 항상 반환값을 받는 쪽이 낫다.

🔴 상속으로 공통 준비를 나누면 테스트 계층이 깊어질수록 **무엇이 준비돼 있는지 읽기 어려워진다.** JUnit 5의 `@ExtendWith`나 별도 Fixture 객체를 조립하는 쪽이 대안이다. 이 볼트에 두 방식을 같은 조건으로 써 본 기록은 없다.
