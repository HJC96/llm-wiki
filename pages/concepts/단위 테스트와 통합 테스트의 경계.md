## 한 줄 정의

> 🟡 **경계는 "무엇을 띄우느냐"가 아니라 "무엇이 깨졌을 때 이 테스트가 실패해야 하느냐"로 정한다.** 도메인 규칙이 바뀌면 단위 테스트가, 외부 계약이 깨지면 통합 테스트가 실패해야 한다.

## 왜 필요한가

로직이 서비스 계층에 몰려 있으면 **작은 규칙 변경도 무거운 통합 테스트로만 확인할 수 있다.** 테스트는 느려지고, 실패했을 때 원인이 규칙인지 배선인지 알 수 없고, 리팩터링할 때마다 깨진다.

> 🔴 반대 방향의 함정도 있다. 내부 구현에 의존하는 테스트만 있으면 **리팩터링에 쉽게 깨지면서 정작 실제 API 회귀는 못 잡는다.** 둘 다 필요하고, 각자 다른 것을 지킨다.

## 어떻게 동작하는가

테스트 피라미드(대략 Unit 70 / Integration 20 / E2E 10)는 개수 비율이 아니라 **책임 분배**로 읽는 게 맞다.

| | 무엇을 지키나 | 깨져야 하는 때 |
|---|---|---|
| **단위** | 도메인 규칙·상태 전이·계산 | 규칙이 바뀌었을 때 |
| **통합** | 배선, 트랜잭션 경계, 실제 SQL, 매핑 | 인프라와의 접점이 바뀌었을 때 |
| **HTTP 통합** | **외부 API 계약** | 응답 형태·상태코드가 바뀌었을 때 |
| E2E | 사용자 흐름 | 흐름 자체가 깨졌을 때 |

🟢 **HTTP 통합 테스트를 따로 두는 이유가 여기서 갈린다.** 내부를 아무리 리팩터링해도 외부 계약이 유지되는지를 확인하는 게 목적이므로, 내부 구현을 알면 안 된다. MockMvc는 서블릿 컨테이너 없이 빠르게, RestAssured는 실제 포트로 — 어느 쪽이든 **검증 대상은 응답 계약**이다.

> 🟡 도메인이 빈약하면 이 분배 자체가 불가능하다. 규칙이 서비스에 있으면 단위 테스트로 뽑을 대상이 없어서 통합·E2E에 편중된다. **테스트 전략을 바꾸려면 [[도메인 모델 패턴]]을 먼저 바꿔야 한다** — 순서가 반대다.

## 코드에 닿는 지점

**테스트 격리는 전략을 골라야 하는 문제다.** `@AfterEach`에서 `deleteAll()`만 하면 데이터는 지워져도 **시퀀스는 유지되어**, 두 번째 테스트가 `id=2`를 받고 `isEqualTo(1L)`이 실패한다.

| 전략 | 속도 | 운영 동작과의 일치 |
|---|---|---|
| `@Transactional` 롤백 | 빠름 | 🔴 커밋이 안 되므로 다른 스레드가 못 본다. 동시성 테스트에 못 씀 |
| `@Sql` 초기화 스크립트 | 중간 | 시퀀스까지 명시적으로 리셋 가능 |
| `@DirtiesContext` | 느림 | 컨텍스트를 매번 새로 만든다 |
| Testcontainers 재기동 | 가장 느림 | 가장 정확 |

## 트레이드오프

| 단위를 늘릴 때 | 통합을 늘릴 때 |
|---|---|
| 빠르고 실패 원인이 좁다 | 실제로 동작하는지를 본다 |
| 🔴 배선이 틀려도 다 통과한다 | 🔴 느리고 실패 원인이 넓다 |
