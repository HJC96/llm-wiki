## 질문

Validation은 DTO에 두는 것 아닌가? 왜 `CourseValidator` 같은 걸 따로 만드는가?

## 답 (짧게)

> 🟡 **"검증"이라고 부르는 게 한 종류가 아니다.** 여섯 가지가 같은 이름으로 불리고 있고, 각자 있어야 할 자리가 다르다. 어디에 둘지는 **이 규칙을 판단하는 데 무엇이 필요한가**가 정한다.

| 종류 | 자리 | 예 |
|---|---|---|
| 입력 형식 | Request DTO | `@NotNull` · `@Size` · `@Email` |
| 객체 자체의 불변식 | Entity / VO | 가격은 0보다 커야 함 |
| 상태 전이 규칙 | Domain | 취소된 주문은 다시 취소 못 함 |
| 유스케이스 수행 조건 | Application Service | 승인된 강사만 강의 개설 |
| **DB 조회가 필요한 복합 검증** | Validator / Policy / Domain Service | 같은 강사의 강의 제목 중복 |
| 최종 정합성 | DB Constraint | UNIQUE · FK · NOT NULL |

## 근거

### 1. 판단 기준은 한 문장으로 줄어든다

> **"이 규칙을 현재 Entity 하나만 가지고 판단할 수 있는가?"**

```java
instructor.ensureCanCreateCourse();              // 자기 상태만 보면 된다 → 도메인
courseRepository.existsByInstructorAndTitle(..); // 다른 Course를 찾아야 한다 → 바깥
```

🟡 **두 번째는 객체 하나로 판단이 불가능하다.** 리포지터리를 도메인 엔티티 안으로 끌어들이지 않으려면 이 검증은 밖에 있어야 한다. Validator·Policy·Domain Service 중 무엇이든, 요점은 **도메인 엔티티가 조회 책임을 지지 않는 것**이다.

### 2. Validator를 빼는 건 Application Service의 고도(altitude)를 지키려는 것

Application Service가 읽혀야 하는 모습은 유스케이스의 흐름이다.

```java
Instructor instructor = instructorFinder.find(request.instructorId());
courseValidator.validateForCreate(instructor, request);
Course course = Course.create(...);
return courseRepository.save(course);
```

Validator가 없으면 여기에 `isActive` 검사, 제목 중복 조회, 금칙어 검사가 줄줄이 인라인된다. 흐름이 세부사항에 묻힌다. [[애플리케이션 서비스]]가 말하는 "얇게 유지한다"가 이 지점이다.

🟢 검증 종류가 `validateForCreate` · `validateForUpdate` · `validateForPublish`로 늘어날 수 있다는 것도 분리 근거다.

### 3. 🔴 그렇다고 전부 Validator로 보내면 안 된다

원문이 스스로 짚은 부분이다. "Instructor가 active인가"는 사실 사용자 입력 검증이 아니고, Application Service나 도메인에 둬도 된다. **Validator는 갈 곳 없는 검증의 쓰레기통이 아니다.**

Validator로 보낼 것은 위 표의 다섯 번째 줄, **외부 데이터가 있어야 판단되는 것**에 한정된다.

### 4. 실패를 모아서 던진다

검증 하나 실패했다고 즉시 예외를 던지지 않는다.

```java
List<String> errors = new ArrayList<>();
checkTitleDuplication(..., errors);
checkForbiddenWord(title, errors);
checkForbiddenWord(description, errors);
if (!errors.isEmpty()) throw new ValidationException(errors);
```

🟡 이건 설계가 아니라 **UX 결정이다.** 요청 → 제목 오류 → 고쳐서 재요청 → 설명 오류 → 또 재요청을 반복시키지 않는다. 즉시 던지기는 코드가 짧고, 모아 던지기는 왕복이 줄어든다.

### 5. 계층마다 같은 규칙이 또 나와도 중복이 아닐 수 있다

> ⚠️ **정정** (2026-09-11, 개정판 기준): splearn은 **DTO를 웹과 애플리케이션이 공유**한다. 그래서 애노테이션 **선언은 한 곳뿐이고 실행만 두 번** 된다. 규칙이 흩어져 불일치가 나는 중복이 아니다. 처음 적을 때 "양쪽에 선언한다"로 읽었는데 사실과 다르다.
>
> 🟡 **진짜 중복은 Web DTO와 Application DTO를 따로 만들 때다.** 그때는 Web이 요청 포맷·API 스펙 종속 관심사를, Application이 계약상 최소 보장 조건을 맡아 역할이 갈린다. **웹 고유 관심사가 실제로 생겼을 때 분리하면 된다.**

DTO를 따로 두는 경우라면 의미가 이렇게 갈린다.

```text
Web DTO         → HTTP 표현이 올바른가
Application DTO → 이 유스케이스를 호출할 자격이 되는가
```

🔴 **Application Service가 Controller를 통해서만 호출된다는 보장이 없다.** Batch·Kafka Consumer·CLI·다른 Application Service가 부를 수 있고, 그 경로는 Web 검증을 지나지 않는다. 입력 포트 자체를 지키려면 Application DTO에도 제약이 필요하다 → [[@Valid와 @Validated]]

반대로 두 DTO가 사실상 같다면 Application Request를 Controller에서 그대로 쓰는 실용적 선택도 성립한다.

## 확신도

**높음** — 표의 여섯 구분과 판단 질문은 원문이 명시한 것이고, 이 볼트의 [[애플리케이션 서비스]] · [[도메인 모델]] · [[애그리거트 경계 정하기]]가 말하는 책임 배분과 어긋나지 않는다.

🔴 다만 **Validator vs Policy vs Domain Service 중 무엇을 고를지는 이 소스가 답하지 않는다.** 원문도 넷을 나란히 놓고 "고려한다"고만 했다.

## 이 답이 바뀔 조건

- 검증이 여러 애그리거트에 걸치기 시작하면 Validator보다 Domain Service나 Policy 객체가 맞을 수 있다
- 복합 검증을 DB 제약만으로 밀어붙이는 사례(UNIQUE 위반을 잡아 메시지로 변환)를 실제로 겪으면 표의 마지막 줄 비중이 커진다 → [[멱등성]]이 같은 구조를 쓴다

## 연결

- [[@Valid와 @Validated]] — 규칙을 **선언**하는 것과 **실행**시키는 것의 구분
- [[애플리케이션 서비스]] — 얇게 유지한다는 원칙의 구체적 적용
- [[도메인 모델]] · [[애그리거트 경계 정하기]] — 자기 상태로 판단 가능한 규칙이 사는 곳
- [[멱등성]] — 사전 검사를 통과해도 DB 제약이 최종 판정한다는 같은 구조
- [[Natural ID]] — UNIQUE 제약이 검증의 마지막 줄에 서는 사례
