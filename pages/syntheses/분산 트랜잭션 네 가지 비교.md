## 질문

2PC · TCC · Saga(Orchestration) · Saga(Choreography) 중 무엇을 언제 고르는가?

## 답 (짧게)

🟡 **기본값은 Saga Orchestration.** 중간 상태 노출이 곧 사고인 영역(결제·정산)에서만 TCC. 처리 시간이 길거나 참여자가 계속 늘어나면 Choreography. 2PC는 사실상 후보가 아니다.

## 근거

| | [[2PC]] | [[TCC]] | Saga (Orch.) | Saga (Choreo.) |
|---|---|---|---|---|
| 원자성을 지키는 주체 | DB + 트랜잭션 매니저 | 앱 (예약 상태) | 앱 (보상 호출) | 이벤트 흐름 |
| 중간 상태 | 락 걸린 미커밋 | 예약됨 (**안 보임**) | 차감됨 (**보임**) | 차감됨 (**보임**) |
| 일관성 | 강한 일관성 | 확정 시점 정합 | [[최종적 일관성]] | [[최종적 일관성]] |
| 자원 점유 | **길다** (Prepare~Commit) | 짧다 | 짧다 | 짧다 |
| 필요 인프라 | XA DB, JTA | 없음 (HTTP+DB) | 없음 (HTTP+DB) | 메시지 브로커 |
| 흐름 파악 | 쉬움 | 쉬움 | 쉬움 | **어려움** |
| 결합도 | 높음 | 높음 | 높음 | **낮음** |
| 클라이언트 응답 | 동기 | 동기 | 동기 | **비동기 + 폴링** |
| 실무 사용 | 거의 없음 | 결제 등 | **많이** | 처리 시간이 길 때 |

### 세 축이 서로 충돌한다

**정합성 ↔ 가용성** — [[2PC]]는 정합성을 최대로 얻고 가용성을 내준다. [[Saga 패턴]]은 반대. [[TCC]]는 그 사이에서 "예약"이라는 애플리케이션 상태로 **락 없이 자원을 붙드는** 절충을 한다.

**즉시성 ↔ 노출** — TCC의 예약은 중간 상태를 외부에 숨긴다. Saga의 즉시 차감은 한 단계가 줄어 단순하지만, 보상 전까지의 불일치가 그대로 보인다.

**가시성 ↔ 결합도** — Orchestration은 코디네이터 하나만 보면 흐름을 알 수 있는 대신 코디네이터가 모든 참여자를 직접 안다. Choreography는 서로를 모르는 대신 **아무도 전체를 모른다.**

### 방식과 무관하게 사라지지 않는 셋

🟡 **[[멱등성]] · 동시 실행 차단 · [[실패 사실의 기록]].**

2PC를 뺀 나머지 전부가 이 셋을 애플리케이션에서 직접 구현해야 하며, 실제로 코드가 늘어나는 곳도 전부 여기다. 🔴 **기법을 고르는 일보다 이 셋을 제대로 만드는 일이 크다.**

### Spring은 메커니즘을 주고 정책은 주지 않는다

| 개념 | 프레임워크가 해 주는 것 | **내가 정해야 하는 것** |
|---|---|---|
| [[Redis 분산락]] | Redis 명령 실행 | 키 네이밍, **TTL 길이**, 해제 위치, 대기 vs 즉시 실패 |
| [[낙관적 락]] (`@Version`) | 버전 조건 UPDATE, 충돌 예외 | **재시도 여부·횟수·경계**(Facade) |
| [[멱등성]] | **없음 — 직접 구현** | 식별자 발급 주체, 이력 스키마, 재요청 응답 |
| [[재시도와 백오프]] (`@Retryable`) | 재시도 루프, 백오프 | `maxAttempts`, `noRetryFor` |
| [[커밋 후 이벤트 발행]] | 콜백 시점 보장 | 유실 허용 여부(Outbox 필요성) |
| [[Kafka 메시지 키와 순서 보장]] | 키 해싱 → 파티션 라우팅 | **무엇을 키로 잡을지** |

🔴 "Spring이 알아서 해 준다"로 끝내면 TTL도 재시도 상한도 메시지 키도 **비어 있는 채로 운영에 나간다.**

## 확신도

**높음** — 표 자체는 원 소스의 6장을 그대로 따랐고, 축의 해석도 소스가 명시한 것이다.

다만 "실무 사용" 행은 **선택 기준이 아니다.** 🔴 Saga Orchestration이 많이 쓰이는 이유는 우월해서가 아니라 **대부분의 서비스가 최종적 일관성을 감당할 수 있기 때문**이다.

## 이 답이 바뀔 조건

- 도메인이 결제·정산 쪽으로 이동하면 TCC가 기본값이 된다
- Transactional Outbox를 실제로 도입하면 Choreography의 유실 리스크가 낮아져 문턱이 내려간다 → [[Outbox 패턴]] 소스 필요
- `deep-dive`의 2PC·TCC 실험에서 나온 **숫자**가 이 표의 "자원 점유" 행을 정량화하면 확신도가 더 올라간다
