## 무엇

인프런 결제 시스템 강의의 PDF 15개를, 결제 흐름 · 정합성 · 메시징 · 장애 복구 · 동시성 제어 다섯 관점으로 통합 분석한 문서. 자료 내용과 "보완·주의점"을 분리해 적어 놓아서, 강의가 말한 것과 운영에 적용할 때 더 봐야 할 것이 구분된다.

## 핵심 주장

1. **결제 시스템의 목표는 승인 성공이 아니라 수렴이다.** 요청·응답·이벤트는 유실되고 중복되지만, 금전 상태 변경은 논리적으로 한 번만 일어나고 외부 PSP와 내부 원장이 결국 일치해야 한다.
2. **완료는 두 종류다.** PSP 승인 성공(`SUCCESS`)과 내부 후처리 완료(`is_payment_done`)를 한 상태로 합치면, 승인은 됐는데 정산이 안 끝난 결제를 찾을 수 없다.
3. **타임아웃은 실패가 아니라 결과 불명이다.** `FAILURE`로 단정하는 순간 "카드는 긁혔는데 내부는 실패"인 건이 영구히 사라진다.
4. **짧은 로컬 트랜잭션 + 명시적 중간 상태 + Outbox**가 기본 골격이다. 외부 API 호출을 DB 트랜잭션 안에 넣지 않고, DB 변경과 메시지 발행을 아무 장치 없이 분리하지도 않는다.
5. **Kafka Transaction은 Kafka 안에서만 원자적이다.** MySQL 커밋까지 묶어 주지 않는다.
6. **온라인 경로가 완벽해 보여도 Recovery Worker와 Reconciliation이 필요하다.** 수동 조작·과거 버그·메시지 누락은 코드가 감지하지 못한다.
7. 가장 중요한 설계 질문 넷 — 중복 실행돼도 안전한가 / 성공인지 실패인지 모르는 상태를 표현할 수 있는가 / 어느 줄에서 죽어도 수렴하는가 / PSP와 내부 원장이 다르면 찾아낼 수 있는가.

## 아직 안 다룬 것

- **환불 · 부분 취소 · Chargeback** — 원문이 "승인 성공만 구현하면 결제 시스템의 절반"이라고 명시했다. 별도 상태 머신과 Reversal Entry 설계가 필요
- **PSP Webhook 검증** — 서명·재전송·순서 역전·중복. Redirect만으로 결과를 확정하지 않는 경로
- **Circuit Breaker · Rate Limiter** — [[Bulkhead]]와 함께 묶이는 셋 중 둘이 아직 페이지가 없다
- **Schema Evolution** — 이벤트 필드 변경 시 구버전 Consumer 호환
- 🔴 **이 소스에는 수치가 없다.** 전부 설계 원칙과 구조다. deep-dive에 payment-system 모듈이 있으므로 [[MOC-실험]] 쪽 lab 페이지로 숫자를 붙일 여지가 크다
- 원문 §24의 **장애 실험 10종**이 그대로 실험 설계서다 (동시 Checkout 100건, 커밋 후 발행 전 kill, 오프셋 커밋 전 kill 등)
