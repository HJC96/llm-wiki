## 무엇

토비의 클린 스프링 — 도메인 모델을 어떻게 잡고, 그것을 담을 그릇으로 왜 헥사고날을 고르는가. 예제 프로젝트는 스프런(Sprun), 첫 도메인은 회원(Member).

## 핵심 주장

1. **도메인 모델의 실체는 문서나 다이어그램이 아니라 팀 사람들 머릿속의 멘탈 모델**이다. 표현물은 공유 수단일 뿐이고, 개발자에게 최종 표현은 코드다.
2. **DDD의 마지막 D는 Design이고, 핵심은 패턴 이름이 아니라 "누가 하느냐"다.** 도메인 엑스퍼트가 참여하고 개발 내내 모델을 함께 발전시키지 않으면 DDD가 아니다.
3. **도메인 모델 패턴은 작업 단위 API를 갖고 있지 않다.** 그래서 얇은 애플리케이션 서비스(도메인 파사드)가 반드시 따라붙는다.
4. **계층형의 제약은 두 개뿐**이다 — 단방향 사용 관계, 제한된 인터페이스로만 사용(계층 격리).
5. **헥사고날이 실제로 요구하는 것도 셋뿐이다** — 두 인터페이스를 애플리케이션이 정의·소유(DIP) / 액터 연결은 런타임 구성(DI) / 포트에 기술 이름 금지. 나머지는 오해다.
6. **헥사고날의 1순위 목표는 테스트다.** 테스트를 만들지 않으면 헥사고날을 하는 게 아니다.
7. 육각형에 의미는 없다. 대칭을 그리기 쉬운 도형이라 골랐을 뿐이고, 진짜 이름은 포트와 어댑터다.

## 기존 위키와의 관계

- **빈 링크 해소**: `[[테스트 가능한 설계란]]` — **참조 9회로 볼트에서 가장 많이 가리켜지던 미작성 페이지**였다
- **연결 정리**: `[[3-Tier와 헥사고날]]`·`[[레이어 의존 방향]]`·`[[의존성 역전과 어댑터]]` 세 개의 빈 링크는 이번에 만든 [[헥사고날 아키텍처]]·[[계층형 아키텍처]]·[[포트와 어댑터]]와 같은 내용이라, 별도 페이지를 새로 만들지 않고 **참조하던 곳(MOC-설계, [[ArchUnit으로 아키텍처 강제하기]])의 링크를 실제 페이지로 돌렸다**
- **보강**: [[ArchUnit으로 아키텍처 강제하기]] — 강제하려던 "레이어 의존 방향"의 근거 페이지가 생겼다

> ⚠️ **원문 오류 (문서가 이미 바로잡음)**: "다용성" → 다형성 / "Alistair Cockbun" → Cockburn / "도메인 주도 개발" → 도메인 주도 **설계**(강의 본인이 앞서 정정함). 원문에 없어 문서가 덧붙인 것 — PoEAA(2002) 출처, 『Implementing DDD』 저자 Vaughn Vernon, 에반스 원저 2003년.
