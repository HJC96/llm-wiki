## 핵심 주장

1. **의존성 방향은 한 문장으로 못 박는다** — 외부(Actor) → 어댑터 → 애플리케이션 → 도메인, 안쪽으로만. **위반 시 빌드 실패.**
2. **슬라이스와 애플리케이션 컴포넌트를 정의한다** — `domain` 아래 첫 패키지 = 애그리거트 하나 = 슬라이스. 도메인 슬라이스 + 애플리케이션 서비스 슬라이스 = 애플리케이션 컴포넌트.
3. **애그리거트 간 참조 규칙이 문장으로 있다** — 다른 애그리거트 루트를 직접 참조해도 된다. 조회 메서드와 레코드 메서드는 되고 **변경 메서드는 안 된다.**
4. **서비스끼리는 포트로만 만난다** — 다른 애플리케이션 서비스의 provided 포트 인터페이스와 DTO는 쓰되 **구현 클래스는 직접 접근하지 않는다.**
5. **슬라이스 간 순환 의존은 금지.** 단방향만 허용.
6. **금지 항목이 명시적이다** — setter 금지, 도메인은 웹 DTO를 직접 받지 않음, 구현 클래스 직접 접근 금지.
7. **용어 사전이 따로 있다** — 한국어 / 영어 / 설명 세 칸. 클래스 이름이 영어 칸과 같다.

## 기존 위키와의 관계

🟢 **오늘 문답으로 만든 페이지들의 근거가 1차 자료로 확인됐다.** 추론이 아니라 팀이 실제로 적어 둔 문장이라는 게 중요하다.

- **보강**: [[Slice와 Layer]] — "슬라이스"와 "애플리케이션 컴포넌트"의 **공식 정의**가 붙었다. 내가 문답에서 재구성한 것과 일치
- **보강**: [[애그리거트 간 참조]] — "조회 메서드와 레코드 메서드는 되고 변경 메서드는 안 된다"가 가이드 문장 그대로다
- **보강**: [[보편 언어]] — 용어 사전 실물. 그동안 개념만 있었다
- **확인**: [[Spring Data Repository 계약]] · [[null 안전성 애노테이션]] · [[@Valid와 @Validated]] — 가이드의 「어댑터 관례」·「도메인 모델 관례」·「서비스 관례」가 각각 같은 내용을 규칙으로 적고 있다
