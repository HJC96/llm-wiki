## 무엇

토비의 클린 스프링 — 앞 강의([[도메인 모델이 이끄는 개발과 헥사고날 아키텍처]])에서 "헥사고날의 오해"로 던져 놓았던 **"도메인 모델과 JPA 데이터 모델을 분리해야 한다"** 를 본격적으로 반박하고, 그 결론을 Member 애그리거트에 적용한다.

## 핵심 주장

1. 분리를 정당화하는 세 이유 중 **하나만 타당하다** — 정말 다른 경우(✅) / 저장 기술 변경(❌ Spring Data의 목표) / 기술 의존(❌ 애노테이션은 주석).
2. **기술 의존적이다 = 그 기술을 안 쓰면 이 코드가 동작하지 않는다.** JPA 라이브러리를 전부 빼도 엔티티 코드는 실행된다.
3. **JPA 스펙 자신이 도메인 모델을 위한 기술이라고 말한다** — 엔티티 정의가 *lightweight persistent domain object*이고, Spring Data `Repository<T, ID>`의 `T`는 "도메인 타입 = 엔티티 = 애그리거트 루트"다.
4. 🔴 **분리의 진짜 대가는 조용히 사라지는 데이터다.** 프로퍼티 하나 추가에 세 군데를 고쳐야 하고, 매핑을 빼먹으면 **에러 없이** 데이터가 유실된다.
5. 남는 불편함(애노테이션이 덕지덕지)은 **`orm.xml`이 애노테이션을 오버라이드**하므로 분리 없이 해결된다. 남길 것은 `@Entity`·`@NaturalId`·관계뿐.
6. **애그리거트 = 애플리케이션 = 패키지 단위.** 루트만 `public`, 내부 엔티티는 `package-private` + 정적 팩토리. 리포지토리는 루트 하나만 두고 `cascade = ALL`.
7. **테스트는 루트를 통해서만.** 애플리케이션을 Provided Interface로만 테스트하는 것과 같은 원리.

## 기존 위키와의 관계

- **보강**: [[헥사고날 아키텍처]]의 오해 ⑤에 종합 페이지 링크가 붙어 논쟁이 닫혔다
- **빈 링크 해소**: `[[애그리거트 경계 정하기]]` (MOC-설계에서 2회 참조. [[Coarse-Grained Lock]]이 기다리던 짝)
- **연결**: [[Optimistic Offline Lock]] — "루트에만 버전을 두면 안 건드린 변경 때문에 충돌 판정을 받는다"가 실무 판단([[MOC-동시성]]의 오프라인 동시성 절)과 정확히 만난다

> ⚠️ **원문 오류 (문서가 이미 바로잡음)**: "데이터 3색" → 데이터 **탐색**(navigation) / "정체성 브릿지" → 정체성 불일치 / "노웨이 SQL" → NoSQL / "빅크립트" → BCrypt / "create-update"라는 값은 없다(`none`/`validate`/`update`/`create`/`create-drop`) / `getInstruction()` → `getIntroduction()`.
> 덧붙인 것 — `@NaturalId`는 **JPA 표준이 아니라 Hibernate 애노테이션**, 현행 패키지는 `jakarta.persistence`.

## 아직 안 다룬 것

- **`ddl-auto` 운영 정책** — `update`의 한계(nullable 미반영, 컬럼 이름 변경 시 옛 컬럼 잔존)까지 관찰했지만 Flyway 전환은 "뒤에서 한다"로 예고만
- **상속 매핑 · 다형성 쿼리** — 패러다임 불일치 다섯 중 이름만 나오고 실제 매핑은 안 다뤘다
- 반대편 주장(『만들면서 배우는 클린 아키텍처』 계열)의 **원문 미확보** — 그래서 종합 페이지의 확신도에 단서를 달았다
- `equals`/`hashCode`를 `AbstractEntity`로 올린다고 했는데 실제 구현은 다음 강의로 넘어갔다 → [[equals와 hashCode]]
