## 무엇

payment-system wallet-service의 정산 처리에서 `@Version` 낙관적 락 충돌을 어떻게 재시도하는가. 강의 내용을 정리한 노트이고, 잘못된 코드 → 왜 안 되는가 → 올바른 구조 순으로 간다.

## 핵심 주장

1. **트랜잭션 안에서 재시도하면 안 된다.** Optimistic Lock 예외가 나는 순간 그 트랜잭션은 rollback-only가 되어, `catch`로 잡아도 다시 쓸 수 없다. 커밋 시점에 `UnexpectedRollbackException`으로 이어진다.
2. 재시도 경계는 트랜잭션 경계보다 **바깥**에 있어야 하고, 실제 저장은 매번 **독립된 트랜잭션**이어야 한다.
3. 재시도할 때 **최신 값을 다시 읽고 연산을 다시 적용한다.** 이전에 계산한 값을 그대로 쓰면 Lost Update가 그대로 재현된다.
4. bounded retry(3회) + base delay + **jitter**. 고정 지연은 충돌한 트랜잭션들을 같은 박자로 다시 만나게 한다.
5. 트랜잭션은 늦게 시작하고 빨리 끝낸다 — 재조회·계산·지연은 전부 트랜잭션 밖.
6. `private` 메서드에는 프록시 기반 `@Transactional`이 안 걸리므로 `TransactionTemplate`을 쓴다.

## 기존 위키와의 관계

- **보강**: [[낙관적 락]] — 기존 페이지는 "재시도는 트랜잭션 밖에서"를 한 줄로만 적고 있었다. **왜** 밖이어야 하는지(rollback-only)가 이번에 채워졌다
- **보강**: [[Lost Update]] — 재시도 시 재계산을 빠뜨리면 같은 문제가 되돌아온다는 경로가 추가됐다
- **연결**: [[프록시 자기호출 문제]] — `TransactionTemplate`을 쓰는 이유가 이 페이지와 이어졌다

## 아직 안 다룬 것

- 🔴 **수치가 없다.** 재시도 횟수 분포, 충돌률, Hot Key일 때 처리량 저하가 전부 미측정. 볼트의 [[선착순 쿠폰 발급 동시성]]에 낙관적 락 3156ms가 있지만 그건 한 트랜잭션 안 경합 기준이라 정산 시나리오와 조건이 다르다
- Spring Retry(`@Retryable`)로 같은 구조를 만들 때의 차이
- 원문의 "동시 업데이트 3개 → version 3, balance 6,000" 예시는 있으나 실행 결과 로그는 없다
