| 1   | **헥사고날은 중첩을 금지하면서, 내부를 컴포넌트로 나눌 수 있다는 게 무슨 뜻인가?**                                                         | 강의에서는 **전체 업무 로직과 외부 기술의 경계**를 헥사고날로 설명하고, 그 내부의 회원·강사 같은 **업무 책임 분할**은 컴포넌트로 설명한다. 내부에 작은 모듈이나 인터페이스를 만들지 말라는 뜻은 아니다.                                                                                        |
| 2   | **큰 애플리케이션이라는 헥사곤 안에 작은 헥사곤을 만들지 말라는 뜻인가?**                                                               | 강의의 설명은 그렇다. 내부는 업무 컴포넌트로 나누고, 웹·DB 어댑터는 전체 업무 코어 밖에 둔다. 각각 독립적인 헥사곤으로 설계한다면 **서로 연결된 여러 헥사곤**으로 본다.                                                                                                          |
| 3   | **레이어드 아키텍처에서는 Service가 다른 Service를 참조하면 안 되는가?**                                                         | 보편적인 금지 규칙은 아니다. 다만 팀이나 프로젝트에서 결합과 순환참조를 막으려고 제한할 수 있다. **한 방향 호출 자체는 순환참조가 아니다.**                                                                                                                            |
| 4   | **서비스 간 순환참조는 무엇인가?**                                                                                     | 강사 서비스가 회원 서비스를 필요로 하고, 회원 서비스도 강사 서비스를 필요로 하는 구조다. 생성자 주입에서는 객체 생성이 막힐 수 있다. **인터페이스만 추가해도 실제 객체가 서로를 요구하면 순환은 남는다.**                                                                                        |
| 5   | **내가 다뤘던 트랜잭션 스크립트 형태의 레거시에서는 왜 서비스 간 호출을 금지했나?**                                                         | 서비스 하나가 완성된 업무 절차라면, 다른 서비스 호출로 원치 않는 부수 작업까지 실행되거나 트랜잭션·변경 영향이 얽힐 수 있다. 이를 막기 위한 프로젝트 규칙이었을 가능성이 있다. **당시 자료가 없어 정확한 이유는 확정하지 못했다.**                                                                         |
| 6   | **애그리거트란 무엇이고, 변경은 어떻게 하는가?**                                                                             | 불변식을 지키며 변경해야 하는 객체들의 단위다. 강의에서는 **루트를 통해 내부 변경을 수행**하고, 다른 애그리거트를 직접 따라가며 변경하는 것은 제한한다.                                                                                                                      |
| 7   | **다른 애그리거트를 객체로 직접 참조해도 되는가?**                                                                            | 강의는 **직접 참조로 시작하고, 필요하면 식별자 참조로 전환**하는 방식을 선택한다. 직접 참조한다고 두 애그리거트가 하나로 합쳐지는 것은 아니다.                                                                                                                           |
| 8   | **다른 애그리거트도 변경해야 한다면 어떻게 하는가?**                                                                           | 강의에서는 **애플리케이션 서비스가 다른 컴포넌트의 제공 인터페이스를 호출**하도록 한다. 엔티티 내부에서 다른 애그리거트를 직접 변경하는 것과 구분한다. 컴포넌트 간 순환 의존성은 금지한다.                                                                                                   |
| 9   | **직접 참조로 객체를 이미 가지고 있는데, 왜 변경 요청에는 ID를 전달하는가?**                                                           | **같은 제공 인터페이스를 외부 어댑터와 내부 컴포넌트가 함께 사용하기 때문**이다. 외부 요청은 대부분 식별자를 전달하므로 인터페이스를 식별자 기반으로 구성하고, 내부 컴포넌트도 그 계약을 사용한다.                                                                                              |
| 10  | **검증 애노테이션은 보통 Web DTO에 넣지 않나? 애플리케이션 DTO에도 넣으면 중복 아닌가?**                                                 | splearn은 DTO를 웹과 애플리케이션이 **공유**하는 구조라서 애노테이션 **선언은 한 곳뿐**이다. 실행이 두 번 될 뿐, 규칙이 흩어져 불일치가 나는 중복은 아니다.                                                                                                            |
| 11  | **그래도 애플리케이션 계층에서 굳이 또 검증할 이유가 있나?**                                                                      | 제공 인터페이스는 컨트롤러만 호출하지 않는다. 배치·메시지 컨슈머·어드민·테스트도 호출한다. 웹에서만 검증하면 **웹 경로만** 안전하다. 포트가 “어댑터가 알아서 걸러줄 것”이라는 가정 위에 서면 안 된다.                                                                                          |
| 12  | **그럼 진짜 중복이 되는 경우는 언제인가?**                                                                                | Web DTO와 Application DTO를 **따로 만들고 같은 규칙을 각각 선언할 때**다. 이때는 Web은 요청 포맷·API 스펙 종속 관심사를, Application은 계약상 최소 보장 조건을 맡아 역할을 나눈다. **웹 고유 관심사가 실제로 생겼을 때 분리하면 된다.**                                                 |
| 13  | **컨트롤러에** `**@Valid**`**를 쓰면** `**@Validated**`**는 따로 안 써도 되나?**                                          | 일반적인 요청 DTO 검증에서는 안 써도 된다. Spring MVC가 직접 검증을 수행하기 때문이다. 파라미터의 `@Validated`는 **검증 그룹을 지정할 때** 사용할 수 있다.                                                                                                       |
| 14  | `**@Valid**`**와** `**@Validated**`**는 어떻게 다른가?**                                                          | `@Valid`는 Jakarta Validation의 **연관 객체에 대한 캐스케이드 검증 표시**이며, MVC에서는 요청 DTO 검증을 시작하는 표시로도 사용된다. `@Validated`는 Spring 기능으로, **검증 그룹 지정**과 **AOP 메서드 검증 대상 지정**에 사용된다.                                             |
| 15  | `**@RequestParam @Min(1)**` **같은 단순 파라미터도 똑같은가?**                                                         | 다르고, **버전 의존적**이다. Framework 6.1 이전에는 일반적으로 클래스의 `@Validated`를 이용한 AOP 검증을 사용한다. 6.1부터는 MVC 내장 메서드 검증을 지원하며, 이를 사용하려면 클래스의 `@Validated`를 제거한다.                                                                |
| 16  | **인터페이스/애플리케이션 서비스에는 어떻게 거는가?**                                                                           | 강의의 Spring AOP 기반 메서드 검증에서는 **서비스 구현체 클래스에 `@Validated`, 포트 인터페이스 파라미터에 제약과 `@Valid`**를 둔다. `@Valid`가 없으면 DTO 내부 필드로 검증이 이어지지 않는다.                                                                            |
| 17  | **인터페이스와 구현체 양쪽에 제약을 걸면 되나?**                                                                             | Bean Validation 스펙상 하위 타입에서 메서드 파라미터 제약을 추가해 **사전조건을 강화하면 안 된다.** 인터페이스에 선언한 제약은 구현체에 상속되므로 구현체에 다시 선언하지 않는다.                                                                                                 |
| 18  | **서비스 계층 검증에서 실무상 걸리는 점은?**                                                                               | AOP 검증의 기본 예외인 `ConstraintViolationException`은 MVC 요청 검증 예외와 다르다. 클라이언트 입력 오류로 처리하려면 `@RestControllerAdvice` 등에서 적절한 응답으로 매핑해야 한다.                                                                            |
| 19  | **JPA, Spring의 JPA 지원, Spring Data JPA는 어떻게 다른가?**                                                        | **JPA**는 ORM 표준이고 Hibernate 같은 구현체가 실제 동작을 수행한다. **Spring의 JPA 지원**은 `EntityManager`, 트랜잭션 관리 등을 Spring과 연결하고, **Spring Data JPA**는 Repository 추상화와 `save()`, `findById()` 같은 기능을 제공한다.                       |
| 20  | **강의의** `**InstructorRepository**`**는 개발자가 그냥 만든 Repository인가?**                                          | 아니다. Spring Data의 마커 인터페이스인 `Repository`를 상속한다. 다만 `JpaRepository`를 상속하지 않고, **현재 컴포넌트에서 필요한** `**save()**`**,** `**findById()**` **같은 메서드만 직접 선언**한다. 구현체는 Spring Data가 만든다.                                 |
| 21  | `**JpaRepository**`**와 일반** `**Repository**`**를 상속하는 방식은 무엇이 다른가?**                                       | `JpaRepository`는 많은 기능을 기본 노출한다. 마커 `Repository`는 아무 메서드도 없어서 **현재 컴포넌트가 실제로 사용하는 저장소 기능만 골라 노출할 수 있다.**                                                                                                      |
| 22  | **Spring Data JPA에서 수정할 때** `**save()**`**를 해야 하는가?**                                                     | 강의에서는 **수정 후에도** `**save()**`**를 호출하는 것을 Spring Data의 사용 규칙으로 권장**한다. 다만 같은 트랜잭션의 영속 엔티티라면 JPA 더티 체킹으로 `save()` 없이도 UPDATE된다.                                                                                 |
| 23  | **그럼 왜 더티 체킹만 사용하지 않고** `**save()**`**를 호출하는가?**                                                          | **더티 체킹은 JPA의 영속성 메커니즘이고,** `**save()**`**는 Spring Data Repository의 저장 계약**이다. 강의에서는 `조회 → 변경 → save`라는 명시적인 Repository 사용 스타일을 선택한다.                                                                         |
| 24  | **Spring Data JPA를 사용하면 더티 체킹은 사용되지 않는가?**                                                                | 아니다. Spring Data JPA도 JPA 위에서 동작하므로 **더티 체킹은 그대로 작동한다.**                                                                                                                                                      |
| 25  | **Spring Data의** `**save()**`**는 내부적으로 무엇을 하는가?**                                                         | JPA 자체에는 `save()`가 없다. Spring Data JPA의 `save()`는 신규 엔티티면 `persist()`, 기존 엔티티면 `merge()`를 사용한다.                                                                                                               |
| 26  | `**save()**`**를 호출하지 않아도 실제 DB에 저장되는가?**                                                                  | **된다.** 쓰기 트랜잭션 안에서 조회한 엔티티가 영속 상태라면 값을 변경하기만 해도 더티 체킹으로 DB에 반영된다. detached 상태 객체는 단순 수정만으로 반영되지 않는다.                                                                                                         |
| 27  | **더티 체킹과** `**save()**`**의 차이를 한마디로 정리하면?**                                                               | **더티 체킹은 JPA가 변경을 감지해 DB에 반영하는 기술적 메커니즘**, `save()`는 **Spring Data Repository가 제공하는 명시적인 저장 API**다.                                                                                                           |
| 28  | **강의에서 테스트를** `**record**`**로 만든다는 것은 무슨 뜻인가?**                                                           | 테스트 대상이 record라는 뜻이 아니라 **테스트 클래스 자체를 record로 선언**한다는 뜻이다. 필요한 Spring Bean을 record component로 받아 생성자 주입을 간결하게 표현한다.                                                                                           |
| 29  | **record로 테스트 클래스를 만들면 어떤 장점이 있는가?**                                                                      | `@Autowired` 필드를 여러 개 선언하거나 생성자를 직접 작성하지 않아도 돼서 **Bean 주입 코드가 간결해진다.**                                                                                                                                        |
| 30  | **record 테스트의 한계는 무엇인가?**                                                                                 | record는 record component 외에 **추가 인스턴스 필드를 가질 수 없다.** `@BeforeEach`에서 fixture를 만들어 필드에 저장하는 구조에는 적합하지 않다.                                                                                                      |
| 31  | **Course와 Curriculum을 DIP로 연결한다는 것은 무슨 뜻인가?**                                                             | **Course가 필요한 검증 기능을 인터페이스로 정의하고, Curriculum이 이를 구현한다.** Course 서비스는 구체 구현체 대신 자신 쪽의 `CurriculumValidator`를 사용한다.                                                                                             |
| 32  | `**CurriculumValidator**`**는 왜 Curriculum이 아니라 Course의** `**required**`**에 두는가?**                         | **이 기능을 필요로 하고 사용하는 쪽이 Course이기 때문**이다. 계약의 소유자는 사용하는 쪽이다.                                                                                                                                                    |
| 33  | **검증 요청에 왜** `**curriculumId**` **대신** `**courseId**`**를 전달하는가?**                                         | Course는 자신이 가진 `courseId`로 검증을 요청하고, 해당 Curriculum을 찾는 책임은 Curriculum 쪽 구현체가 담당하도록 하기 위해서다.                                                                                                                   |
| 34  | `**CurriculumCoordinator**`**,** `**CurriculumFinder**`**,** `**Curriculum.validate()**`**는 각각 무엇을 하는가?** | Coordinator는 포트를 구현해 **조회와 검증을 연결**하고, Finder는 `courseId`로 Curriculum을 찾으며, 실제 도메인 검증 규칙은 `Curriculum.validate()`가 담당한다.                                                                                      |
| 35  | **Course가 Curriculum의 기능을 호출하는데, 어떻게 의존성이 역전된 것인가?**                                                      | **실행 시 호출 방향과 코드 의존 방향이 다르기 때문**이다. Course와 Curriculum 구현체 모두 Course 쪽 인터페이스를 바라보게 해 컴파일 타임 의존 방향을 역전한다.                                                                                                      |
| 36  | **커리큘럼 검증 예외를 Course에서 잡는 이유는 무엇인가?**                                                                     | 오류를 무시하는 것이 아니라 **다른 강의 검증 오류와 함께 모아 전달하기 위해서**다.                                                                                                                                                             |
| 37  | **심사 신청에서 검증했는데 공개할 때도 다시 검증하는 이유는 무엇인가?**                                                                | **심사 신청 후 커리큘럼이 변경될 수 있기 때문**이다. Publish 시점에도 현재 상태가 유효한지 다시 확인해야 한다.                                                                                                                                         |
| 38  | **DB에** `**S1 → S2 → S3**` **순서로 INSERT하면 조회할 때도 같은 순서로 나오지 않나?**                                         | 아니다. `**ORDER BY**`**가 없는 DB 조회 결과 순서는 보장되지 않는다.** Java `List`의 위치를 유지하려면 별도 순서 정보가 필요하다.                                                                                                                     |
| 39  | `**section_order**` **없이** `**id**`**로 정렬하면 되지 않나?**                                                      | 중간 삽입·이동이 있으면 안 된다. **ID는 “누구인가”, order는 “몇 번째인가”**를 나타낸다.                                                                                                                                                    |
| 40  | **JPA의** `**@OrderColumn**`**은 왜 사용하는가?**                                                                 | Java `List`의 **위치 정보를 DB에도 저장하기 위해서**다. JPA가 order 컬럼을 관리하고 삽입·삭제·이동 시 값을 갱신한다.                                                                                                                               |
| 41  | `**removeLesson()**`**에서 L1을 제거했을 때** `**lesson_order**` **변경은 정상적으로 DB에 반영된 것인가?**                       | 그렇다. 남은 L2의 `lesson_order`가 1 → 0으로 변경된 것은 정상이다. 문제는 **제거된 L1 row 자체가 삭제되지 않았던 것**이다.                                                                                                                         |
| 42  | **List에서는 L1이 없어졌는데 왜 DB에는 L1이 남았나?**                                                                     | `@OrderColumn`은 **남아 있는 요소들의 순서만 관리**한다. Collection에서 빠진 엔티티를 자동 DELETE하지는 않는다.                                                                                                                               |
| 43  | **DB에는 제거된 L1이 어떤 상태로 남았을까?**                                                                             | 스크립트만으로 정확한 컬럼값은 확정할 수 없지만, **연관관계에서는 빠졌지만 row는 남은 고아 데이터 상태**로 이해할 수 있다.                                                                                                                                     |
| 44  | **그럼** `**orphanRemoval=true**`**를 사용하면 해결되지 않나?**                                                        | 단순 삭제만 있다면 해결된다. 하지만 이 도메인에는 Lesson을 다른 Section으로 **이동**하는 기능이 있어서 사용하지 않았다.                                                                                                                                  |
| 45  | **Lesson 이동 때문에 왜** `**orphanRemoval**`**을 사용할 수 없나?**                                                    | 이동은 기존 Section List에서 제거 후 새 Section List에 추가하는데, `orphanRemoval=true`이면 제거 시점에 **삭제 대상으로 판단될 수 있어 이동 의도와 충돌**한다.                                                                                             |
| 46  | **그래서 실제 Lesson 삭제는 어떻게 처리하는가?**                                                                          | 도메인에서는 Collection에서 제거한 Lesson을 반환하고, 애플리케이션 서비스가 `lessonRepository.delete(removed)`를 호출해 **실제 DB DELETE를 명시적으로 수행**한다.                                                                                       |
| 47  | **Course 생성 시 Curriculum도 같이 만들려고 하니 왜 순환 의존성이 생겼나?**                                                     | 기존 `Curriculum → Course` 의존에 Course에서 Curriculum 구현체를 직접 호출하는 `Course → Curriculum` 의존이 추가되어 순환이 생겼다.                                                                                                         |
| 48  | **DIP는 그냥 구현체 대신 인터페이스를 사용한다는 뜻인가?**                                                                      | 아니다. 핵심은 **인터페이스의 소유권까지 역전하는 것**이다. 상위 모듈이 필요한 계약을 정의하고 하위 모듈이 구현해야 한다.                                                                                                                                       |
| 49  | **왜** `**CurriculumCreator**` **인터페이스를 Curriculum이 아니라 Course 쪽에 두는가?**                                   | 이 기능을 **필요로 하는 쪽이 Course이기 때문**이다. Course가 자신에게 필요한 계약을 정의하고 Curriculum이 구현한다.                                                                                                                                |
| 50  | **Course가 Curriculum 기능을 호출하는데 어떻게 의존 방향은** `**Curriculum → Course**`**가 되는가?**                           | 런타임에는 Course 요청으로 Curriculum 기능이 실행되지만, 컴파일 타임에는 Curriculum 구현체가 Course 쪽 인터페이스를 구현하므로 **코드 의존성은 Curriculum → Course**가 된다.                                                                                   |
| 51  | **DIP가 되는 이유는 컴파일 타임에 어떤 구현체가 들어올지 모르기 때문인가?**                                                            | 일부 맞지만 핵심은 **구현체를 모르는 것보다 컴파일 타임 의존 방향이 역전됐다는 것**이다.                                                                                                                                                          |
| 52  | **그러면 실제** `**CurriculumCoordinator**`**는 언제 연결되는가?**                                                     | **런타임에 Spring DI가 연결한다.** DIP는 의존 방향 설계 원칙이고, DI는 실제 객체를 연결하는 방법이다.                                                                                                                                           |
| 53  | **인터페이스를 Curriculum 쪽에 두고 Course가 그것만 참조해도 구현체는 모르니 괜찮지 않나?**                                             | 아니다. 인터페이스 자체가 Curriculum 모듈에 있으면 Course를 컴파일하기 위해 Curriculum 모듈이 필요하므로 **Course → Curriculum 의존성이 그대로 남는다.**                                                                                                 |
| 54  | **DIP와 DI를 한마디로 어떻게 구분하면 되는가?**                                                                           | **DIP는 컴파일 타임 의존 방향을 설계하는 원칙, DI는 런타임에 실제 구현 객체를 연결하는 방법**이다.                                                                                                                                                 |
| 55  | **개발 가이드를 문서로 만들어 두는 것이 왜 중요한가?**                                                                         | 팀의 설계 원칙·표준·정책을 사람 기억에만 의존하지 않고 코드 리뷰·온보딩·AI 코딩의 기준으로 재사용하기 위해서다.                                                                                                                                             |
| 56  | **AI에게 개발 가이드를 Harness로 준다는 것은 무슨 뜻인가?**                                                                  | AI가 매번 다른 스타일로 코드를 만들지 않도록 **팀의 설계 규칙을 지속적으로 적용하는 제약과 기준**으로 사용하는 것이다. 문서 자체도 Harness 역할을 할 수 있다.                                                                                                             |
| 57  | **강의에서 말하는 Slice는 어떤 기준으로 나누는가?**                                                                         | 도메인에서는 `domain` 바로 아래 패키지를 하나의 Slice로 취급한다. `domain.member`, `domain.instructor` 등이 각각 Slice가 된다.                                                                                                             |
| 58  | `**Shared**`**는 Aggregate가 아닌데 왜 하나의 Slice로 취급하는가?**                                                      | Aggregate는 아니지만 **의존성 관점에서 독립 단위처럼 취급**할 수 있다. 다른 Slice가 Shared를 의존하고 Shared는 반대로 의존하지 않도록 한다.                                                                                                                |
| 59  | **Layer와 Slice는 무엇이 다른가?**                                                                                | **Layer는 기술적·아키텍처 역할에 따른 수평 분리**, Slice는 같은 Layer 내부에서 **업무 책임에 따라 나눈 단위**다.                                                                                                                                  |
| 60  | **ArchUnit에서 Slice 간 순환 의존성은 어떻게 검사하는가?**                                                                 | `SlicesRuleDefinition.slices()`로 Slice를 나눈 뒤 `beFreeOfCycles()`를 적용해 순환 코드 의존성을 자동 검사한다.                                                                                                                      |
| 61  | `**Instructor → Member**`**처럼 한 방향 의존성이 있으면 ArchUnit 테스트가 실패하는가?**                                        | 아니다. 한 방향 의존은 허용된다. 반대 방향까지 생겨 `Instructor ↔ Member`가 되어야 순환이다.                                                                                                                                               |
| 62  | **ArchUnit 테스트가 성공하는 것만 확인하면 충분한가?**                                                                      | 아니다. 의도적으로 규칙을 위반하는 의존성을 만들어 **실제로 테스트가 실패하는지도 검증해야 테스트 자체를 신뢰할 수 있다.**                                                                                                                                       |
| 63  | **실제 실행 흐름과 코드의 의존 방향은 왜 구분해야 하는가?**                                                                      | 런타임 호출 방향과 컴파일 타임 의존 방향은 다를 수 있다. 헥사고날/DIP에서는 **외부 구현이 내부 인터페이스에 의존하도록 코드 방향을 역전**할 수 있다.                                                                                                                     |
| 64  | **Aggregate가 다른 Aggregate를 직접 참조하는 것 자체도 금지되는가?**                                                         | 아니다. 강의에서는 다른 Aggregate의 **조회는 허용**하지만 다른 Aggregate의 상태 변경 메서드를 직접 호출하는 것은 제한한다.                                                                                                                              |
| 65  | **왜 다른 Aggregate의 조회는 허용하면서 변경은 막는가?**                                                                    | 다른 Aggregate의 상태까지 자유롭게 변경하면 **Aggregate의 변경 책임과 경계가 흐려지기 때문**이다. 변경은 담당 Application Component의 제공 인터페이스를 통해 요청한다.                                                                                            |
| 66  | **ArchUnit에 “다른 Aggregate의 getter만 호출 가능” 같은 규칙이 기본으로 있나?**                                               | 없다. 이런 프로젝트 고유 규칙은 `ArchCondition` 등을 이용해 직접 구현해야 한다.                                                                                                                                                         |
| 67  | **커스텀** `**ArchCondition**`**은 다른 Slice 호출인지 어떻게 판단하는가?**                                                 | 각 클래스의 메서드 호출 대상을 조사하고, 같은 Slice면 허용하며 **다른 Slice에 속한 클래스일 때만 추가적인 호출 규칙을 검사**한다.                                                                                                                             |
| 68  | **다른 Slice에서는 구체적으로 어떤 메서드만 허용하는가?**                                                                      | 강의에서는 getter, `isXXX`, record accessor처럼 **상태 조회 성격의 메서드만 허용**하고 다른 Aggregate의 상태 변경 메서드 호출은 실패시키도록 한다.                                                                                                       |
| 69  | **이런 Aggregate 접근 규칙도 굳이 자동화해야 하는가?**                                                                     | 프로젝트가 커질수록 리뷰만으로 놓칠 수 있으므로 **문서에는 원칙을 남기고, 기계적으로 판별 가능한 부분은 ArchUnit 테스트로 자동화**한다.                                                                                                                            |
| 70  | **이번 강의에서 ArchUnit을 사용하는 핵심 목적은 무엇인가?**                                                                   | 패키지 검사 자체보다 **팀의 아키텍처 원칙을 실행 가능한 테스트로 만들어 코드가 계속 원칙을 지키는지 자동 검증하는 것**이다.                                                                                                                                      |
| 71  | **신규** `**CourseDetail**`**인데 왜** `**Detached Entity**` **오류가 발생했나?**                                     | 실제로 DB에 저장됐다가 detached 된 것이 아니라 **Fixture가 신규 객체에 ID를 미리 넣어 둔 것이 문제**였다. `Course`는 신규여서 `persist()`되는데 cascade된 `CourseDetail`에 ID가 이미 있어 Hibernate가 신규 엔티티로 보지 못해 `detached entity passed to persist`가 발생했다. |
| 72  | **신규 Entity Fixture에서는 ID를 어떻게 해야 하는가?**                                                                  | DB가 ID를 생성하는 엔티티라면 Fixture에서도 보통 **ID를** `**null**`**로 둔다.** 임의의 ID를 넣으면 Hibernate의 신규/기존 엔티티 판단을 방해할 수 있다.                                                                                                   |
| 73  | **Spring Data JPA** `**save()**`**에서** `**merge()**`**가 호출되면 전달한 객체 자체가 managed가 되는가?**                   | 아니다. `merge()`는 전달받은 detached 객체의 상태를 **별도의 managed 객체에 복사하고 그 managed 객체를 반환**한다. 따라서 `save()`의 반환값을 사용하는 것이 안전하다.                                                                                           |
| 74  | **Repository 테스트에서** `**flush()**`**와** `**clear()**`**를 왜 같이 사용하는가?**                                    | `flush()`는 변경사항을 DB에 반영하고, `clear()`는 영속성 컨텍스트를 비운다. 이후 조회하면 1차 캐시가 아닌 **DB에서 실제로 다시 읽어오는 상황을 테스트**할 수 있다.                                                                                                    |
| 75  | **검증 로직을 왜** `**CourseValidator**` **같은 별도 클래스로 분리하는가?**                                                  | Application Service가 `조회 → 검증 → 생성 → 저장` 같은 **유스케이스 흐름에 집중하도록**, 중복 확인·금지어 확인처럼 커질 수 있는 검증 세부사항을 분리한 것이다. 모든 검증을 Validator에 넣는다는 규칙은 아니다.                                                                     |
| 76  | **검증은 DTO, Domain, Application 중 어디에 두어야 하는가?**                                                           | `@NotNull`, `@Size` 같은 입력 형식은 DTO, 객체 스스로 판단 가능한 불변식·상태 전이는 Domain, DB 조회나 다른 Aggregate가 필요한 유스케이스 검증은 Application Service·Validator·Policy 등을 고려한다.                                                          |
| 77  | **검증 위치를 판단할 때 쓸 수 있는 기준은 무엇인가?**                                                                         | **“이 규칙을 현재 Entity 하나만 가지고 판단할 수 있는가?”**가 유용하다. 가능하면 Domain 쪽, 외부 조회가 필요하면 Application 쪽에 둘 가능성이 높다.                                                                                                          |
| 78  | `**BaseApplicationServiceTest**`**가** `**abstract class**`**이면** `**prepareMember()**`**도 추상 메서드인가?**     | 아니다. `abstract class`와 `abstract method`는 별개다. 구현부가 있는 `prepareMember() { ... }`는 일반 메서드이고, 진짜 추상 메서드는 `abstract Member prepareMember();`처럼 구현부가 없다.                                                          |
| 79  | **Base Test를 왜** `**abstract class**`**로 만드는가?**                                                          | 이 클래스 자체를 테스트하거나 직접 생성하려는 것이 아니라 **공통 fixture와 helper를 자식 테스트에 제공하는 기반 클래스**이기 때문이다.                                                                                                                          |
| 80  | **부모 테스트 클래스의** `**protected Member member**`**는 어떻게 자식에서 사용할 수 있는가?**                                    | `protected` 필드와 메서드는 자식 클래스에서 사용할 수 있다. 부모 객체가 따로 있는 것이 아니라, **자식 객체 안에 부모로부터 상속된 필드와 메서드가 함께 존재**한다고 이해하면 된다.                                                                                                |
| 81  | `**prepareMember()**`**가 왜** `**this.member**`**를 계속 덮어쓰는가?**                                             | `prepareMember()`는 고정 Member 하나를 돌려주는 함수가 아니라 **새 테스트 Member를 준비하는 factory/helper**다. 호출할 때마다 새 Member를 만들고 `this.member`에는 가장 최근 값을 저장한다.                                                                    |
| 82  | **기존** `**member**`**를 계속 재사용하면 안 되는가?**                                                                  | 한 명만 필요하다면 재사용해도 되지만, 테스트에서 서로 다른 Member 여러 명이 필요할 수 있다. 기존 객체만 반환하게 만들면 `member1`, `member2`가 같은 객체가 되어 여러 fixture를 만들 수 없다.                                                                                 |
| 83  | **공통 테스트 필드 때문에 실제 테스트가 왜 깨졌나?**                                                                          | `setUp()`에서 `this.instructor = A`를 저장해 뒀는데 테스트 중 `prepareInstructor()`를 다시 호출하면서 **공통 필드가 B로 덮어써졌다.** 테스트는 여전히 A라고 생각하고 사용해서 잘못된 객체로 조회하게 됐다.                                                                 |
| 84  | **같은 타입의 Fixture가 여러 개 필요한 테스트에서는 어떻게 하는 것이 안전한가?**                                                       | `this.instructor` 같은 공통 mutable field에 의존하지 말고 `Instructor instructor1`, `instructor2`처럼 **반환값을 지역변수로 명시적으로 저장해서 사용**하는 것이 안전하다.                                                                              |
| 85  | `**@ToString(callSuper = true)**`**는 무엇인가?**                                                              | Lombok이 만든 `toString()`에 **부모 클래스의** `**toString()**` **결과도 포함**하라는 뜻이다. `AbstractEntity`의 ID 같은 정보까지 출력할 수 있다.                                                                                               |
| 86  | `**@ToString(exclude = {...})**`**는 왜 사용하는가?**                                                            | 특정 필드를 `toString()`에서 제외한다. JPA 연관관계를 출력하면 **LAZY 조회, 지나치게 큰 출력, 양방향 관계 순환참조**가 발생할 수 있어 `member`, `course`, `instructor` 같은 연관 필드를 제외하는 경우가 많다.                                                              |
| 87  | `**@NaturalId**`**는 무엇인가?**                                                                               | JPA 표준이 아니라 **Hibernate가 제공하는 Natural Key 표현용 애노테이션**이다. DB가 생성한 PK와 별개로, 업무적으로 엔티티를 자연스럽게 식별하는 값을 표시한다.                                                                                                      |
| 88  | **Enrollment에서는 왜** `**Member**`**와** `**Course**`**에** `**@NaturalId**`**가 붙는가?**                        | Enrollment의 의미가 **“어떤 회원이 어떤 강의를 수강한다”**이므로 `(member, course)` 조합이 업무적으로 Enrollment 하나를 식별한다. 또한 Enrollment 생성 후 이 두 값은 변경하지 않는다고 보기 때문이다.                                                                    |
| 89  | **Enrollment의** `**(member, course)**`**가 Natural ID이면 JPA 복합 PK인가?**                                     | 아니다. 실제 JPA PK는 `AbstractEntity`의 `@Id`다. `(member, course)`는 **업무상의 복합 Natural Key**일 뿐이다. 진짜 복합 PK라면 `@EmbeddedId`, `@IdClass` 등을 사용한다.                                                                     |
| 90  | `**@NaturalId**`**와 DB** `**UNIQUE**` **제약은 무엇이 다른가?**                                                    | `@NaturalId`는 **도메인적으로 이 값이 엔티티의 정체성이라는 의미**를 표현하고, UNIQUE Constraint는 **DB에서 실제 중복 저장을 막는 정합성 장치**다.                                                                                                         |
| 91  | **Course의** `**(instructor, title)**`**도 Unique인데 왜 Natural ID가 아닌가?**                                    | **Unique하다고 모두 Natural ID인 것은 아니다.** Course의 `title`은 나중에 변경할 수 있어 안정적인 정체성이라고 보기 어렵다. Enrollment의 `member`, `course`는 생성 후 변경하지 않는다.                                                                         |
| 92  | **Natural ID를 판단할 때 중요한 특징은 무엇인가?**                                                                       | 단순히 고유한 것뿐 아니라 **엔티티의 정체성을 나타내고 생명주기 동안 안정적으로 유지되는가**를 봐야 한다.                                                                                                                                                 |
| 93  | `**jakarta.annotation.Nonnull**`**과** `**jakarta.validation.constraints.NotNull**`**은 무엇이 다른가?**          | `Nonnull` 계열은 주로 **코드 계약과 IDE·정적 분석을 위한 nullability 정보**이고, `jakarta.validation.constraints.NotNull`은 **Bean Validation이 런타임에 실제로 검사하는 constraint**다.                                                         |
| 94  | **왜** `**@Nonnull**`**을 붙였는데 Spring Method Validation에서 null이 막히지 않았나?**                                  | `@Nonnull`이 Bean Validation constraint가 아니기 때문이다. 그래서 Validation Proxy를 통과해 서비스와 Repository까지 진입했다. `@NotNull`로 바꾸자 메서드 진입 전에 `ConstraintViolationException`이 발생했다.                                           |
| 95  | `**@Valid**`**,** `**@Validated**`**,** `**@NotNull**`**의 관계를 어떻게 기억하면 되는가?**                             | `@NotNull`은 **검증 규칙**, `@Valid`는 **객체 내부의 constraint까지 따라 들어가 검증하라는 표시**, `@Validated`는 **Spring Bean의 Method Validation을 활성화하는 역할**로 이해하면 된다.                                                                |
| 96  | `**Section**` **코드에서** `**this**`**는 항상 같은 Section인가?**                                                   | 아니다. `this`는 **현재 실행 중인 메서드를 호출한 객체**다. `A.method(B)`라면 `method()` 내부의 `this`는 A다.                                                                                                                            |
| 97  | `**s2.moveAllLessonsTo(s1, 2)**`**에서** `**this**`**와** `**target**`**은 무엇인가?**                            | `moveAllLessonsTo()` 내부에서 `**this = s2**`, `target = s1`이다. 즉 `this`는 Lesson을 내보내는 source Section이고, `target`은 Lesson을 받을 destination Section이다.                                                              |
| 98  | `**moveAllLessonsTo()**` **안의** `**target.addLesson()**`**에서는 왜** `**this**`**가 달라지는가?**                  | `target.addLesson()`은 실제로 `s1.addLesson()`을 호출하는 것이므로 `**addLesson()**` **내부의** `**this**`**는 s1**이 된다. `this` 자체가 이동하는 게 아니라 각 메서드를 호출한 객체가 다르기 때문이다.                                                        |
| 99  | **Lesson을 다른 Section으로 옮길 때 왜** `**lesson.moveTo(this)**`**도 호출하는가?**                                     | target의 `lessons` List에 넣는 것만으로는 Lesson이 가진 `section` 참조가 이전 Section을 가리킬 수 있다. 그래서 **Lesson 자신의 Section 참조도 target으로 변경**해야 한다.                                                                              |
| 100 | `**moveAllLessonsTo()**`**에서 왜 target에 add한 뒤 source에서 remove도 해야 하는가?**                                  | 이동은 **목적지에 추가 + 출발지에서 제거**가 모두 필요하다. 처음 구현에서 remove를 빼먹어 source List가 영원히 비워지지 않았고 while문이 무한 반복되어 `OutOfMemoryError`가 발생했다.                                                                                  |
| 101 | `**moveAllLessonsTo()**`**에서 왜** `**while**`**을 사용했는가?**                                                  | 원본 List를 순회하면서 동시에 요소를 제거해야 하기 때문이다. `forEach`로 순회 중 구조를 변경하는 것보다 **첫 요소를 이동하고 제거하는 과정을 List가 빌 때까지 반복**하는 방식을 선택했다.                                                                                          |
| 102 | **Lesson 이동 시 왜** `**insertIndex++**`**가 필요한가?**                                                          | Lesson의 기존 순서를 유지하기 위해서다. `[L0, L1]`을 모두 index 0에 넣으면 `[L1, L0]`로 순서가 뒤집히므로 `0`, `1`, `2`처럼 삽입 위치를 증가시킨다.                                                                                                     |
| 103 | **첫 번째 Section을 삭제하면 Lesson은 어디로 이동하는가?**                                                                 | 앞 Section이 없기 때문에 **다음 Section의 앞부분**으로 이동한다. 기존 전체 Lesson 순서를 유지하기 위해 insert index를 0부터 증가시킨다.                                                                                                               |
| 104 | **중간이나 마지막 Section을 삭제하면 Lesson은 어디로 이동하는가?**                                                             | **이전 Section의 뒤쪽**으로 이동한다. 이전 Section의 `lessons.size()`를 시작 insert index로 사용하면 기존 Lesson 뒤에 이어 붙일 수 있다.                                                                                                       |
| 105 | **Section을 삭제한 뒤 index 계산이 왜 헷갈렸나?**                                                                      | List에서 요소를 먼저 삭제하면 뒤의 요소들이 앞으로 당겨져 **index가 즉시 바뀌기 때문**이다. `[S0, S1]`에서 S0을 삭제하면 기존 S1이 바로 index 0이 된다.                                                                                                       |
| 106 | **마지막 남은 Section은 왜 삭제할 수 없도록 했나?**                                                                       | Curriculum에는 최소 하나의 Section이 있어야 한다는 **도메인 규칙** 때문이다. 단순 `IndexOutOfBoundsException`이 나게 두기보다 의미 있는 `IllegalStateException`으로 규칙을 코드에 드러낸다.                                                                   |
| 107 | `**SectionContent**`**,** `**LessonContent**` **record는 왜 만들었나?**                                         | 복잡한 `Curriculum → Section → Lesson` Entity 그래프를 테스트에서 쉽게 비교하기 위해 **현재 구조를 단순 값으로 복사한 Snapshot 객체**로 만든 것이다.                                                                                                   |
| 108 | **테스트 Snapshot을 만들면 어떤 장점이 있는가?**                                                                         | `getSections().get(0).getLessons()...`처럼 깊게 탐색하지 않고, **Section 제목과 Lesson 순서를 한눈에 비교**할 수 있어 테스트가 읽기 쉬워진다.                                                                                                    |
| 109 | **Snapshot 테스트에서 static factory와 varargs를 왜 사용하는가?**                                                      | `new SectionContent(...)`, `List.of(...)`가 반복되면 테스트의 핵심 구조가 잘 보이지 않는다. `section("S0", lesson("L0"), lesson("L1"))`처럼 만들어 **테스트가 실제 Curriculum 구조처럼 읽히도록** 하기 위해서다.                                            |
| 110 | **Curriculum, Section, Lesson의 책임을 어떻게 나눴나?**                                                             | **Curriculum은 어느 Section을 변경·삭제하고 어디로 이동할지 결정**, Section은 자신의 Lesson 목록 추가·삭제·이동을 담당하고, Lesson은 `moveTo()`를 통해 **자신이 속한 Section 상태를 변경**한다.                                                                   |
| 111 | **이번 Section 이동 코드에서** `**this**`**를 가장 간단히 어떻게 기억하면 되는가?**                                               | `moveAllLessonsTo()`에서는 `**this = source**`**,** `**target = destination**`, 그 안에서 `target.addLesson()`으로 들어가면 **`addLesson()`의 `this = destination`**이라고 기억하면 된다.                                            |
| 112 | `**@NonNullApi**`**는 무엇을 하는 애노테이션인가?**                                                                    | 패키지에 적용해서 **그 패키지의 메서드 파라미터와 반환값을 기본적으로 Non-Null이라고 선언**한다. 메서드마다 `@NonNull`을 반복해서 붙이지 않아도 된다.                                                                                                                |
| 113 | `**@NonNullApi**`**는 왜** `**package-info.java**`**에 작성하는가?**                                              | `@NonNullApi`는 개별 클래스가 아니라 **패키지 전체에 적용하는 애노테이션**이기 때문이다. `package-info.java`를 이용하면 `tobyspring.splearn.application` 같은 패키지의 기본 null 정책을 한 곳에서 선언할 수 있다.                                                      |
| 114 | `**@NonNullApi**`**가 붙어 있으면 모든 값에 실제 null 검사가 수행되는가?**                                                    | 아니다. `@NonNullApi`는 주로 **nullability 계약을 IDE와 정적 분석 도구에 알려주는 역할**을 한다. `Objects.requireNonNull()`처럼 런타임에서 자동으로 null을 검사해 주는 기능은 아니다.                                                                          |
| 115 | `**@NonNullApi**`**가 적용된 패키지에서 특정 파라미터나 반환값만 null을 허용하려면 어떻게 하는가?**                                       | 해당 위치에 `**@Nullable**`**을 명시**하면 된다. 즉 기본값은 Non-Null로 두고, 예외적으로 null이 가능한 API만 `@Nullable`로 표시하는 방식이다.                                                                                                        |
| 116 | `**@NonNullApi**`**와** `**@NotNull**`**은 어떻게 다른가?**                                                       | `@NonNullApi`는 패키지의 **기본 nullability 계약을 선언하는 용도**이고, Bean Validation의 `@NotNull`은 **실행 시 실제 null 여부를 검증하는 제약 조건**이다. 따라서 `@NonNullApi`만으로 Spring Method Validation이 수행되는 것은 아니다.                             |
| 117 | **필드에도** `**@NonNullApi**`**가 적용되는가?**                                                                    | 아니다. `@NonNullApi`의 기본 Non-Null 정책은 **메서드 파라미터와 반환값**을 대상으로 한다. 필드에 대한 기본 Non-Null 정책은 별도의 `@NonNullFields`가 담당한다.                                                                                            |
| 118 | **최신 Spring에서도** `**@NonNullApi**`**를 계속 사용하는가?**                                                         | Spring Framework 7에서는 `@NonNullApi`가 deprecated 되었고 **JSpecify의** `**@NullMarked**` **사용을 권장**한다. 다만 이 프로젝트처럼 이전 Spring null-safety 방식을 사용하는 코드에서는 `@NonNullApi`를 볼 수 있다.                                     |
