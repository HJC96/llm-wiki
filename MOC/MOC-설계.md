# MOC — 설계

← [[MOC-홈]]

이 축이 이력·면접에서 가장 많이 쓰인다. 개념보다 **판단 기준**을 남기는 게 목적.

## 객체지향

- [[책임을 어디에 둘 것인가]] — 서비스인가 도메인인가
- [[서비스 계층의 책임]] 🟡 — 유스케이스 조율까지. 규칙은 도메인으로
- [[if 분기가 쌓일 때 전략 패턴]] — 클래스 수가 느는 비용을 감수하는 기준
- [[포트와 어댑터]] ✅ — Required Interface를 **애플리케이션이 소유**한다. DIP 그 자체
- [[불변 객체]] · [[값 객체와 엔티티]]

## DDD

문제 → 해결 순서. 소스는 [[도메인 모델이 이끄는 개발과 헥사고날 아키텍처]] · [[JPA와 도메인 모델 분리 논쟁]]

- [[도메인 모델]] ✅ — 개념·관계·규칙의 지도. 실체는 문서가 아니라 팀의 멘탈 모델
- [[DDD]] ✅ 🔴 — 마지막 D는 Design. 패턴 이름 모음이 아니고, 현업 전문가가 빠지면 DDD가 아니다
- [[보편 언어]] ✅ — 대화·문서 **그리고 코드**가 같은 어휘를 쓴다
- [[도메인 모델 패턴]] ✅ — 단순 / 풍성한 / 🔴 애니믹(이건 패턴이 아니다)
- [[애플리케이션 서비스]] ✅ — 도메인 모델에 없는 **작업 단위 API**를 채우는 얇은 층
- [[애그리거트 경계 정하기]] ✅ — 생명주기를 함께하는 것끼리. 루트만 public, 내부는 package-private
- [[애그리거트 간 참조]] ✅ 🔴 — 직접 참조해도 된다. 갈리는 건 **조회냐 변경이냐**
- [[Natural ID]] ✅ 🔴 — Unique하다고 전부 Natural ID가 아니다. **생명주기 동안 안정적**이어야 한다
- [[애그리거트 루트를 통한 변경]] · [[도메인 이벤트]]
- [[바운디드 컨텍스트]]
- [[DDD를 어디까지 적용할 것인가]] 🔴 — 전부에 적용하지 않는다

## 아키텍처

- [[계층형 아키텍처]] ✅ — 제약은 둘뿐이다. 단방향 사용 + 제한된 인터페이스
- [[헥사고날 아키텍처]] ✅ 🔴 — 실제 요구는 셋뿐. 육각형에 의미는 없고 오해가 다섯 개
- [[포트와 어댑터]] ✅ — Provided(롤리팝) / Required(소켓)
- [[모듈 간 순환 의존]] ✅ 🔴 — 같은 DIP를 **모듈 ↔ 모듈 가로 축**에 적용. 인터페이스를 만드는 게 아니라 **소유권**을 옮긴다
- [[Slice와 Layer]] ✅ — Layer는 수평(기술), Slice는 수직(업무). 헥사곤 안에 헥사곤을 만들지 않는다
- 소스: [[클린스프링 DIP로 모듈 순환 끊기]] · [[클린스프링 전체 문답 118]] · [[Splearn 개발가이드와 용어사전]]
- **[[도메인 모델과 JPA 엔티티를 분리해야 하는가]]** ⭐ — 아니다. 분리의 대가는 조용히 사라지는 데이터
- [[orm.xml로 매핑 걷어내기]] ✅ — 분리하지 않고 애노테이션만 걷어내는 법
- [[모놀리식에서 서비스를 쪼갤 때 생기는 것]] → [[MOC-분산시스템]]

## 테스트

- [[테스트 가능한 설계란]] ✅ 🟡 — 테스트하기 어려우면 설계가 잘못된 신호. **테스트도 액터다**
- [[단위 테스트와 통합 테스트의 경계]] ✅ — 경계는 "무엇을 띄우느냐"가 아니라 "무엇이 깨졌을 때 실패해야 하느냐"
- [[테스트 더블]] — Mock, Stub, Fake를 언제
- [[HTTP 통합 테스트]] — 내부가 바뀌어도 외부 계약이 유지되는지
- [[Testcontainers]] ✅ — H2의 가짜 안정감을 피하는 법. 랜덤 포트를 `@DynamicPropertySource`로
- [[Testcontainers 테스트 인프라]] ✅ — 위를 실제로 돌려본 실험
- [[ArchUnit으로 아키텍처 강제하기]] ✅ — 코드리뷰로 지키던 합의를 CI가 지키게
- [[테스트 픽스처 상속 구조]] ✅ 🔴 — 반복은 줄지만 데이터 출처가 흐려진다. 권장 패턴이 아니라 편의 설계
- [[레거시에 테스트를 붙이는 순서]] 🟡 — 구조를 바꿀 곳과 입출력만 고정할 곳을 구분

## 동시성 패턴 (PoEAA 16장)

락 종류를 고르는 문제가 아니라 **정합성의 단위를 어디로 잡을까**의 설계 판단.

- [[업무 트랜잭션과 시스템 트랜잭션]] ✅ 🟡 — 두 단위가 어긋나는 자리에서 모든 게 시작된다
- [[Optimistic Offline Lock]] ✅ — 낙관이 기본값. 검증 성공이 곧 락 획득
- [[Pessimistic Offline Lock]] ✅ 🔴 — 실패 비용이 크면 뒤집힌다. 고아 락이 실제 운영 부담
- [[Coarse-Grained Lock]] — 애그리거트 경계와 락 단위가 만나는 지점 → [[애그리거트 경계 정하기]]
- [[조회와 저장이 다른 요청일 때 무엇으로 막는가]] ✅ — 네 선택지 비교

## 판단 기준

여기가 이 MOC의 핵심.

- **[[검증 로직은 어디에 두는가]]** ⭐ — 검증 6분류. 기준은 "현재 Entity 하나만으로 판단 가능한가"
- [[개발 가이드 문서]] ✅ — 규칙을 한 파일에 적어 두고, 기계가 판별 가능한 것만 테스트로 내린다
- [[언제 추상화하지 않을 것인가]] 🟡 — 전략 패턴은 도입, OpenSearch는 미도입
- [[새 기술을 들이기 전에 묻는 것]] — "지금 가진 걸로 풀 수 있나"
- [[운영 가능성을 설계 기준으로 쓰기]]
