# MOC — 동시성

← [[MOC-홈]]

문제에서 해결로 내려가는 순서로 배열.

## 문제부터

- [[경쟁 상태]] — 읽기와 쓰기 사이의 틈에서 생기는 모든 것
- [[잃어버린 갱신]] — 두 트랜잭션이 같은 값을 읽고 각자 덮어쓸 때
- [[중복 처리]] — 인스턴스가 여러 대일 때 같은 작업을 두 번 하는 것

## 스레드를 안 묶는 법

- [[블로킹과 비동기는 다른 축]] ✅ — 두 축은 독립. `@Async` + JDBC는 비동기지만 논블로킹이 아니다
- [[이벤트 루프와 스레드 점유]] ✅ 🔴 — "기다림에는 스레드가 필요 없다". 단일 요청은 오히려 느리다
- [[Reactor]] ✅ — 그 모델을 타입으로 표현한 라이브러리

## 한 프로세스 안에서

- [[synchronized의 동작]] — 모니터 락. 왜 분산 환경에선 안 통하는지
- [[volatile과 가시성]] · [[Java 메모리 모델]]
- [[스레드 풀 크기 결정]]
- [[암달의 법칙]] ✅ — 코어를 늘려도 직렬 구간은 안 줄어든다

## DB로 푸는 법

- [[원자적 UPDATE로 푸는 동시성]] — 락을 안 잡고 푸는 가장 싼 방법
- [[조건부 상태 전이 선점]] ✅ — 조건부 UPDATE에 성공한 쪽만 처리. 실무 적용
- [[원자적 UPDATE로 푸는 동시성]] ✅ — 읽지 않고 쓴다. 틈 자체를 없앤다 (369ms)
- [[비관적 락]] ✅ — `FOR UPDATE`로 차단. 경합이 잦을 때 (429ms)
- [[낙관적 락]] ✅ — 막는 게 아니라 **감지**하는 장치. 재시도는 트랜잭션 밖에서
- [[낙관적 락 재시도 경계]] ✅🔴 — **왜** 밖이어야 하나. 충돌한 트랜잭션은 rollback-only라 재사용할 수 없다
- [[외래키 제약과 락 경합]] ✅ — FK·UNIQUE가 조용히 거는 S 락과 승격 데드락
- [[Lost Update]] ✅ — 낙관적 락이 푸는 문제. 락 단위가 어긋나면 안 막힌다
- [[네임드 락]] ✅ — DB를 락 저장소로 쓰기. 트랜잭션이 아니라 **세션**에 종속된다

## 요청이 나뉘면 (오프라인 동시성)

조회와 저장이 별도 요청이면 위의 락들은 그 구간을 덮지 못한다. 정합성 책임이 DB에서 애플리케이션으로 넘어오는 층.

- [[업무 트랜잭션과 시스템 트랜잭션]] ✅ — 사람이 느끼는 단위와 DB가 보장하는 단위는 다르다
- [[Optimistic Offline Lock]] ✅ — 버전을 클라이언트가 들고 나갔다 돌아온다. 충돌은 **끝에서** 드러난다
- [[Pessimistic Offline Lock]] ✅ — 시작 전에 점유. 대가는 동시성과 고아 락 운영
- [[Coarse-Grained Lock]] — 연관 객체 묶음을 락 하나로. 락 단위(입도)를 정하는 짝 패턴
- [[조회와 저장이 다른 요청일 때 무엇으로 막는가]] ✅ — 네 선택지 비교. **여기부터 읽어도 된다**

## 분산 환경에서

- [[Redis 분산락]] ✅ — SETNX + TTL + `finally` + 소유권 확인. 락이 트랜잭션보다 바깥
- [[Redis 분산락의 함정]] 🔴 — TTL 만료와 GC 정지가 겹칠 때
- [[Cache Stampede]] ✅ — 인기 키 만료 순간의 동시 miss. 분산 락 + DCL로 합친다
- [[캐시 정합성 Race Condition]] ✅ — 읽기와 쓰기가 교차해 옛 값이 뒤늦게 눌러앉을 때
- [[Redisson 동작]] — 락 연장(watchdog), 재진입
- [[멱등성]] ✅ — 락은 **동시**를, 멱등성은 **순차**를 막는다. 둘은 짝이다
